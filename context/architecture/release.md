# Release — the native build, native dependency patches and the shipped payload

## Purpose

How PocketPal's Android artifacts get their llama.rn native payload (build mode, compiled variants, the Hexagon/NPU backend), and the payload gate that runs before any Android artifact is uploaded. What the gate checks is enforced by its script and fails loudly; this doc holds what CI cannot tell you. It also holds the iOS React Native build mode, the native dependency patches, whisper.rn's Android CPU variants (patch, #1019), iOS llama.rn, built from source with its Metal libraries, and iOS whisper.rn, built from source into the same executable with its own precompiled Metal library (#1020). Not covered: signing, version bumping, and TestFlight and Play metadata. `model-loading.md` owns runtime Hexagon device selection and the llama.rn version rationale.

**Not on `main` yet:** open PR #869 adds publish-ordering tests, 16 KB alignment checks, and top-level payload assets. The previous version of this doc described them (`git show 1ad6ce1:context/architecture/release.md`); distill them back in when it lands.

## How it works

1. Each Android building job sets `ORG_GRADLE_PROJECT_rnllamaBuildFromSource: 'true'` and exports the manifest's variant allowlist as `ORG_GRADLE_PROJECT_rnllamaVariants`. llama.cpp compiles from source.
2. `setup-hexagon-sdk` provisions the SDK. The Hexagon backend compiles into `rnllama_v8_2_dotprod_i8mm_hexagon_opencl` only when the SDK roots and `libcdsprpc.so` exist. `syncRNLlamaHtpAssets` copies the five DSP libraries (v73–v85) into `assets/ggml-hexagon/`.
3. A log grep for `Building rnllama variants: <list>` proves the allowlist reached gradle. Then the gate runs on the exact paths about to be uploaded.
4. Release only: (pending PR) both jobs set `PLUS_STORE_GATE: 'true'` in their job env, and `verify-plus-gate.sh --gated` checks the APK and AAB; then upload to Play, push the version tag, and attach the APK to the GitHub Release. iOS checks the IPA after the payload check, before `upload_to_testflight`.
5. At runtime, `RNLlama.loadNative` walks the ladder (hexagon_opencl → dotprod_i8mm → dotprod → i8mm → v8_2 → v8 → generic `rnllama_jni`), then loads `rnllama` unconditionally.
6. iOS: `pod install` runs with the build mode fixed. Before compile, the script phase compiles the kernel set into `rnllama.metallib` and the tensor API kernels into `ggml-tensor.metallib`. At registry init ggml loads `rnllama.metallib` from the main bundle; on tensor GPUs it also loads `ggml-tensor.metallib` and uses its `mul_mm`/`fa_tensor` functions over the base ones. (#1020) A second phase compiles whisper's library (`rnwhisper.metallib`, pending PR; `default.metallib` on `main`); at first dictation whisper's ggml loads it through `bundleForClass` (the main bundle, `whisper-rn` being static) on every GPU, tensor forced off.

## Traps and decisions

**Build mode and the backend**
- **The root `android/gradle.properties` is not a lever.** llama.rn's own `gradle.properties` wins for its subproject (measured on Gradle 9.0.0, re-checked on 9.4.1 by the allowlist grep; pending PR). Only `ORG_GRADLE_PROJECT_…`, `-P`, or a `$GRADLE_USER_HOME/gradle.properties` override it, and the last is live because `release.yml` points `GRADLE_USER_HOME` at `runner.temp`. Build mode is always declared in the job, never inferred.
- **Every way of losing the Hexagon backend is silent.** A missing SDK directory prints one line, a missing `libcdsprpc.so` is a CMake warning, and missing DSP sources skip the sync. The build succeeds each time. That shipped once (issue #858), which is why the check sits on the artifact.
- **Backend presence is read from `.dynsym`, never `strings` or file size.** Both give false results. The #858 APK had all 12 libraries and all 4 DSP assets, so only the symbol rule would have failed it.
- **Symbol names match exactly.** From llama.rn 0.13.0-rc.5, ggml symbols are unprefixed, and each older `lm_` name ends with its successor, so a suffix or substring reader would pass an old artifact. The gate's fixtures keep the `lm_` names as defined noise for that reason.
- **Local builds are a coin toss.** `build.gradle` defaults `HEXAGON_SDK_ROOT` to an SDK directory, so the backend is included only if that directory exists. From llama.rn 0.13.0-rc.8 the default is `~/.hexagon-sdk/6.7.0.0` (tools `21.0.04`), but CI provisions 6.4.0.2, so a local build exports both `HEXAGON_SDK_ROOT` and `HEXAGON_TOOLS_ROOT`; without them the backend is silently omitted. The rc.9 host sources (rc.9 adds `htp-kparams`, `htp-opnode`, `htp-fusion`) compile against 6.4.0.2, so the pin stays (pending PR). Run the gate locally to find out. A macOS host can build it: nothing on the Android path invokes `hexagon-clang`.
- **The gate proves presence, not engagement.** `isHexagonSupported()` gates the backend on SoC hints at runtime, and no emulator has a DSP.
- **ggml-opencl compiles every program at backend init and `exit(1)`s on a compile failure** (pending PR). Each bump adds programs (rc.9: 18), and only a device driver proves them. The lab's Adreno drivers are newer than those behind the 1.17.2 crash, so each bump that adds programs files a Play vitals watch for `ggml-opencl` crashes.
- **The escape hatch is `-PrnllamaBuildFromSource=false`**, not the default. The JNI wrapper would link against a prebuilt from another snapshot, and struct-layout drift wouldn't surface.
- **Consume llama.rn npm releases, not git refs.** A git install lacks `bin/`, `jniLibs`, `lib/`, and the QAIC `vendor/llama.cpp/ggml/src/ggml-hexagon/htp/v73` artifacts.

**The llama.rn patch**
- **It ships on both platforms**: llama.rn compiles from source in every Android and iOS build, and `yarn install` re-applies the patch even on a `node_modules` cache hit. The `src/index.ts` hunk is in the JS bundle and carries no native marker. On iOS the CI payload check finds the core marker. Locally, after a patch change, remove `node_modules/llama.rn` and run `yarn`.
- **The patch is proven on the artifact, not trusted.** It exports `rnllama_patch_abort_v3` (core, every `librnllama_*.so`) and `rnllama_jsi_patch_ownership_v3` (every `librnllama_jni*.so`); the manifest demands them as `kind: patch-marker` rules, with a `why` explaining the miss. An unpatched or prebuilt (`-PrnllamaBuildFromSource=false`) artifact fails the gate. Bump the suffix whenever the patch's contract changes.
- **`patches/**` is in every `node_modules` and `.cxx` cache key in `ci.yml`**, so a patch edit never meets stale patched or compiled sources.
- **A llama.rn bump makes `patch-package` fail loudly or needs a re-port.** Re-port against the new sources (the patch names its version), keep the markers, and re-run the device release matrix (`model-loading.md`, Verification). From rc.6, upstream's `ContextClaim` (a raw pointer) replaces the `isContextBusy` / `throwIfContextBusy` the patch rewrote around `ContextRef`: declare the claim after the ref so it is destroyed first. The patch is the llama.rn fork fixes (context ownership, the abort callback, the end-of-completion trim, the stop re-apply) plus the markers (the rc.8 re-port dropped the inert JSI trim helper and framework-headers guard). Every `llama_context` the rn context creates carries the abort callback: the target's is set right after a successful load and before any draft load, and `createMTPDraftContext` sets it on whatever it returns (MTP or draft-simple), outside the `is_mtp` branch that keeps `ctx_other`. `~llama_rn_context` clears both before teardown.
- **A local build on the Linux aarch64 host cannot link `hexagon_opencl`** (qemu segfaults the link). Build with `ORG_GRADLE_PROJECT_rnllamaVariants=rnllama,rnllama_v8_2_dotprod` and check the markers with `readelf -W --dyn-syms`; that APK fails the full gate by design.

**The Phonon add-on**
- **A missing Phonon library ships silently.** The probe reports `library-missing` or `unsupported-abi` and the engine is just hidden, so check the artifact: both `.so` in `lib/arm64-v8a/`, `Stored`, `zipalign -c -P 16` OK. The payload manifest does not cover them.
- **The add-on peers a narrow core range** (0.1.2 and 0.1.3: `>=2.7.0 <2.9.0`): its engine SDK is experimental, so a core bump outside it is an ERESOLVE; bump core and add-on together.

**The variant ladder**
- **Rung 6 (`rnllama_v8`) is not a duplicate of the generic `rnllama`.** Non-generic arches add optimised ARM sources; dropping rung 6 silently demotes pre-fp16 devices to portable C.
- **`rnllama_v8_2_dotprod_i8mm` and the hexagon variant share arch and flags.** An "equal flags means covered" rule would wrongly license dropping the hexagon variant.
- **`v8_2_i8mm` is the one dropped rung**, a costed bet: no shipping SoC is known to report i8mm without dotprod. Upstream's 3-variant CI list demotes every non-Snapdragon arm64 device to generic; don't copy it.
- **The allowlist grep proves the env route only because `rnllamaVariants` is set in no properties file.** Adding it to one keeps the grep green while it proves nothing. The grep literal is upstream's println; reword it when upstream does.

**react-native-enriched-markdown** (pending PR)
- **Its postinstall downloads the tree-sitter runtime (github.com) and grammar sources (registry.npmjs.org), sha256-verified, and a failed download still lets the install succeed.** Code highlighting is enabled explicitly so that a missing grammar fails the native build instead of shipping plain code blocks.
- **A cached `node_modules` could keep a failed download forever** (the cache key is `yarn.lock` + `patches/**`), so every workflow that installs before a native build re-runs `INIT_CWD="$GITHUB_WORKSPACE" node node_modules/react-native-enriched-markdown/postinstall.mjs`; it is a no-op when the vendored assets match their `.stamp`.
- **The script reads the app's block only through `INIT_CWD`.** Run directly without it, the config is `{}`, math and highlighting default on, and it downloads RaTeX. Yarn v1 also hides a dependency's lifecycle output, so check the lines by running the script directly.
- **iOS reads the block at `pod install`, not at build time**: after editing it, run `pod install` and build clean. The Android `.so` must be 16 KB page-aligned.

**pdfbox-android and PDFKit** (pending PR)
- `PdfTextModule` (`documents.md`) uses `com.tom-roush:pdfbox-android:2.0.27.0` (Apache-2.0; bundles LiberationSans, SIL OFL 1.1, and Adobe CMaps / glyph list under the Apache PDFBox NOTICE). The AAR is 3.25 MB. Measured APK delta against `main` (E2E release APK, BouncyCastle excluded, 0 `org.bouncycastle` classes): +2,740,658 bytes raw, +2,651,473 bytes download (classes plus 125 font / CMap assets). Re-measure on each bump.
- **BouncyCastle is excluded** (`exclude group: "org.bouncycastle"` in `android/app/build.gradle`, about 8 MB more otherwise). Only `PublicKeySecurityHandler` / `SecurityProvider` use it (certificate-encrypted PDFs, refused anyway); password and RC4/AES standard encryption use `javax.crypto`. `PublicKeySecurityHandler` is loaded for every encrypted PDF, but no BouncyCastle type appears in a class-level signature of the four security classes (`javap -p … | grep -v '(' | grep -c bouncycastle` is 0 for each), so loading it needs none. Re-run that check on a bump; a certificate-encrypted PDF fails as `NoClassDefFoundError`, caught as `E_PDF_UNREADABLE`.
- Release minify is off; the AAR ships consumer keep rules for when it is turned on.
- iOS links `PDFKit.framework` explicitly in the app target's Link Binary phase and imports it with `#import <PDFKit/PDFKit.h>` (C++ modules are off in `.mm`, so `@import` fails). No Podfile change.

**iOS Metal libraries**
- **A library that is found but cannot load is fatal at context init, not registry init**: every model load fails (`model-loading.md`). ggml looks in its class's bundle (the main bundle, `llama-rn` being static), then next to the executable.
- **Libraries kept apart by name** (pending PR): llama.rn looks up only `rnllama` and `ggml-tensor`, whisper.rn only `rnwhisper` (lookup hunk; on `main` it looks up `default`). The lookup, the script's output, the Podfile output and the payload check's required name are one string, and `ios-llama-metal.test.js` pins their agreement: a half-rename loses whisper's Metal silently, since without its library whisper finds no kernel sources at the root, fails its Metal init and transcribes on the CPU after the probe. The payload check rejects a root `default.metallib`.
- **An incremental local build keeps a stale `default.metallib`** in the built `.app` after the rename (pending PR). Nothing looks it up, but the payload check fails on it; build clean.
- **whisper's library is non-tensor on every GPU** (#1020): `WSP_GGML_METAL_TENSOR_DISABLE=1` at launch forces `has_tensor` off, so one precompiled library (iOS 18 target, bf16) serves every device and whisper never compiles shaders at runtime. Unlike llama.rn, whisper ships no tensor override library, so tensor GPUs run its standard kernels (cost unmeasured, no tensor device in the lab).
- **whisper.rn carries a stale `cpp/ggml-metal-impl.h`** next to the live `cpp/ggml-metal/ggml-metal-impl.h`. The library must compile from the live one, which the host code includes, with only `WSP_GGML_METAL_HAS_BF16` defined.
- **Both ggml copies link into one executable** (#1020), and hidden visibility does not keep two static libraries apart. ld does not fail either: built without the renames, the app linked with 6 duplicate-symbol warnings, keeping one copy of each `ggml::cpu` destructor and typeinfo, and of the weak vtables. Hence the `-D` renames and the symbol gate, which judges every identifier in a shared name (a `std::` instantiation over a first-party type is first-party). A new DENY is a new rename in the podspec hunk; only a name from a third-party header joins the allowlist.
- **Header maps are off for both ggml pods** (#1020). Xcode header maps index every Pods target's headers by basename and are searched before `-I`, so each copy's `ggml.h` and `ggml-impl.h` resolved to the other's. A quoted ggml include in either pod now resolves only through that pod's own directories.
- **Cost of whisper from source** (#1020): IPA +3.35 MB over llama.rn from source (whisper's library 13.45 MB raw); a clean `whisper-rn` compile takes 25 s against `llama-rn`'s 49 s; CI `build-ios` time is about the same as #1016's.
- **Tensor GPUs get upstream's override library**. Whenever `has_tensor` is true, `ggml-metal-device.cpp` sizes every `mul_mm` (bf16 included) for the tensor kernel, so `ggml-tensor.metallib` must be built with bf16 as well as `GGML_METAL_HAS_TENSOR`; upstream's CMake omits bf16 there. Xcode 26.0.1 (SDK 26.0) rejects tensor `mul_mm` with bf16; 26.6 (the macos-26 runner default) and 27.1 build it, so the README floor is 26.6. If the override library is missing or fails to load, ggml turns the tensor API off and runs the base kernels; a missing or unloadable `rnllama.metallib` is fatal to Metal init. ggml routes by function name, so the override library must hold every kernel the host sizes for tensor (today all of `mul_mm.metal` and `fa_tensor.metal` from llama.rn 0.13.0-rc.8 and rc.9; `fa_f16` until rc.7: the only kernels that read `GGML_METAL_HAS_TENSOR`; `fa_tensor.metal` also compiles into `rnllama.metallib`, empty). A missing one makes a tensor GPU ask the base library for a kernel that compiled empty there, and flash attention fails on every non-vec prefill. On a tensor GPU every function the override library holds replaces the base one by name, so all of `mul_mm.metal`, the MoE kernels included, runs from it; rc.9 changed that MoE path (pending PR). Forced on an A15, its output was bit-identical to the runtime-compiled tensor kernels for the rc.7 set; the rc.8 set loaded with no pipeline error and answered coherently there (output not compared).
- **bf16 must be compiled in.** Upstream's precompiled path omits it, and an A15 reports `has_bfloat`. The library's iOS 18 target and bf16 kernels are why the launch gate exists (`model-loading.md`).
- **The committed kernel phase is `pod install` output.** The `[CP-User] Build llama.rn Metal kernels` phase in `project.pbxproj` carries the kernel arguments (from `GGML_METAL_LIBS`) and `inputPaths` (the `kernels/` listing). A llama.rn bump commits the regenerated pbxproj with `Podfile.lock`; otherwise a build that skips `pod install` misses new kernels and the next `pod install` dirties the tree. `ios-llama-metal.test.js` fails on a stale phase (rc.8 added `fa_tensor` and `mul_mv_mma`).
- **Embedding off is two edits together**: the flag and the `.s` glob.
- **llama.rn's host code builds with the prebuilt framework's flags** (#1026): `-O3 -DNDEBUG`, as its CMake Release build, and nothing else: no `-funroll-loops`, no `-mcpu` (`RNLLAMA_NATIVE_CPU` stays off; llama.rn's example app sets `-mcpu=apple-m2`, which would SIGILL older devices). Upstream's podspec adds `-funroll-loops`; with it, Metal decode on an iPhone 13 Pro averaged 14–20% below 1.21.0 once the phone was warm (up to about 55% in long hot runs) and matched it when cool, while prefill and the GPU kernels were unaffected. Kernels, pipelines, CPU ISA and thread layout were identical, so the cost is per-token host code. On each llama.rn upgrade, re-port the flag line in the podspec hunk (`ios-llama-metal.test.js` pins it); judge Metal speed only in interleaved runs (1.21.0 and the build alternating), since phone heat alone moves a cell by 2x.
- **Kernels compile in parallel through positional `xargs -n1 sh -c`, never `-I`.** BSD `xargs -I` substitutes only into arguments up to 255 bytes; archive paths are longer, and the archive's library lost kernels. The script checks every `.air` before linking.
- **x86_64 simulator links fail** on `arch/arm` quants: simulators build arm64 only, on an Apple silicon Mac.
- **Xcode 26 needs the Metal toolchain component.** `ci.yml` and `release.yml` provision it; the script fails with the install hint. The tensor kernels need Xcode 26.6 or later; on an older Xcode the script names that floor when a tensor compile writes no `.air`.
- **No simulator run exercises the library.** The gate is on in every simulator (its GPU is below Apple6), and the app keeps the GPU off on simulators anyway, so the payload check is the only guard before a device.
- **CI builds the device slice, not the simulator** (pending PR). `build-ios` builds `Release` for `-sdk iphoneos` (signing off): same build time, one extra scan, and the gates read what ships, the linked executable included. A simulator-only compile break (`TARGET_OS_SIMULATOR` paths) is no longer caught in CI; local dev runs build the simulator.
- **The AMX scan counts only AMX-encoded words** (undecoded words in the `0x00201000` opcode space), not raw `<unknown>`: jump tables show as `<unknown>` too (`libllama-rn.a` has 4). It calibrates on an assembled AMX instruction. The App Store rejects AMX opcodes (ITMS-90755). (pending PR) It scans `libllama-rn.a`, `libwhisper-rn.a` and the device executable, which carries every static library the app links (Phonon's included). `scan()` streams `llvm-objdump` into `awk` inside a plain `counts=$(…)` under `pipefail`, so a failing objdump fails the step; `local x=$(…)` or `< <(…)` would hide it and read as 0 AMX words.
- **On each llama.rn upgrade**, re-check the podspec hunk, the lookup hunk, `GGML_METAL_LIBS` and the `-mtargetos` value, and diff the vendored `common/chat.h`, `common.h`, `rn-llama.h` and `rn-completion.h` against every member `ios/PocketPal/AppIntents/LlamaContextWrapper.mm` reads: it is the app's only C++ consumer of llama.rn, only an iOS build compiles it, and the reads must match llama.rn's own JSI (rc.8 made `common_chat_params::prompt` a `common_chat_prompt`, flattened with `.str()`; rc.9 only added members); on a whisper.rn upgrade, its lookup names, `WSP_GGML_METAL_LIBS`, kernel helpers with an extension other than `.metal`/`.h` (not declared as phase inputs, so incremental builds would keep a stale library), both `WSP_GGML_METAL_*` env names, the stale-header layout, and that every hunk still applies.

**whisper.rn variants** (#1019)
- **The Java predicate is the only SIGILL guard.** whisper.rn's ggml has no runtime CPU dispatch on Android (`ggml-cpu/arch/arm/cpu-feats.cpp` is not compiled; the dotprod paths are compile-time `__ARM_FEATURE_DOTPROD`), so a rung must require every feature in its `-march`; `whisper-dotprod-ladder.test.js` (#1021) pins the dotprod rung's guards, the cpuinfo tokens each guard is computed from (assigned once), and the build flags. The ladder is dotprod → fp16 → v8 → generic, one library per process; a failed load falls through.
- **The payload gate does not cover whisper libraries.** A missing dotprod library ships silently and only slows transcription, so check the artifact. `postinstall.sh` runs `patch-package --error-on-fail`, so a patch that no longer applies fails `yarn install`.
- **Upstream 0.8 builds prebuilts from one shared variant list** (`android/src/main/cmake/rnwhisper-build-options.cmake`), and its `_hexagon` rung outranks every CPU rung on Snapdragon 8-series phones with fp16-only flags. Dropping the patch needs the dotprod variant in the published jniLibs and a dotprod-compiled `_hexagon` (prepared on the `a-ghorbani/whisper.rn` branch `android-dotprod-variant`, not proposed upstream yet), confirmed by logcat on a Hexagon-eligible phone and on a Pixel.

**Held by review, not by CI**
- **The gate runs before every upload, on the same paths.** The fastlane lanes are split so the gate can sit between build and upload; nothing tests the ordering.
- **`upload_android_alpha`'s `aab:` must match the gate's `--aab` in `release.yml`.** It is one path written twice. Without an explicit `aab:`, the lane goes green having uploaded no binary.
- **The manifest can be weakened and still pass**, for example with a symbol rule re-pointed at `librnllama.so`. The script enforces floors, not meaning; the control is a reviewed manifest diff.
- **Test builds may add instrumentation, never subtract capability.** `e2e-tests.yml` provisions the SDK and runs the gate exactly as release does.
- **Bump the SDK version and both digests together**, in `setup-hexagon-sdk` only.
- (pending PR) **`PLUS_STORE_GATE: 'true'` lives in the job env** of `build_android` and `build_ios`, not a step or the `.env` heredoc, so the Gradle daemon and `gym` inherit it. The `--gated` check comes before every publish step, on the same files.

**JS build flags** (pending PR)
- **The bundle task ignores env changes unless they are inputs.** `createBundle*JsAndAssets` declares no env input, so a rebuild that only flips a babel-folded env var stays UP-TO-DATE and ships the old bundle; Metro's `--reset-cache` never gets to run. A new babel env flag joins the inputs in `android/app/build.gradle`.
- **From-source builds stay ungated.** An F-Droid-style `assembleProdRelease` sets no app env, so no flavor, properties file or metadata may set `PLUS_STORE_GATE` or `E2E_BUILD`. `ci.yml`'s `--ungated` steps guard that path.

**CI hygiene**
- **`print_command: false` on both `gradle(...)` calls.** Fastlane's command echo leaked the signing passwords into the build log.
- **`RNLLAMA_SKIP_POSTINSTALL=1` (release, e2e) is safe only when building from source.** `ci.yml` doesn't set it in the jobs that save its `node_modules` cache, which is shared with `build-and-test`; only the restore-only `perf` job does.
- **The `perf` job measures base, then head, in one checkout** (#996; `scripts/perf-compare.sh`). It restores the shared `node_modules` key and never saves it: it installs other commits' dependencies and skips llama.rn's native postinstall, and the build jobs consume that key. A `yarn.lock` or `patches/**` difference forces a clean install on both sides, because patch-package can't re-patch already-patched files. The script runs from inside one `main()`, since the base checkout replaces it mid-run. Base's `yarn test:perf [--baseline]` is invoked by head's script, so that command is a cross-commit interface. The clean-tree check runs before `.reassure/` is wiped and ignores untracked files. In CI the exit trap returns to the start ref without reinstalling head's dependencies; locally it reinstalls them.
- **No ccache on the release path**: a prefix restore could link objects of unreviewed provenance into the shipped binary. In `ci.yml`, ccache needs `CCACHE_COMPILERCHECK=content` plus the sloppiness list, or every lookup misses and it looks like a cold cache.
- **GitHub caps caches at 10 GB per repo and evicts silently.** An evicted SDK or ccache entry shows only as a slow run. `ci.yml` `build-android` takes about 44 min cold and 23 min warm.
- **Enabling release minify needs a `-keep class com.rnllama.**` rule.** None exists.
- **Play Billing comes only from `react-native-iap`.** `openiap-versions.json` in the package pins `openiap-google`, which brings `billingclient:billing` 9.x; the app declares no billing dependency, so check `./gradlew :app:dependencies --configuration prodReleaseRuntimeClasspath | grep billingclient` after a library bump. iOS gains the `NitroIap`, `NitroModules` and `openiap` pods.

**React Native upgrades and native dependency patches**
- **iOS uses RN's prebuilt core and deps** (`RCT_REMOVE_LEGACY_ARCH=1`, Hermes V1 forced). 0.86.3's prebuilt core broke `RNFBApp` under `use_frameworks! :static` (non-modular React-Core headers) and needed `RCT_USE_PREBUILT_RNCORE=0`; 0.87.1's builds it. `pod install` only adds project settings: after a switch, diff `project.pbxproj` against a fresh install.
- **`RCTCxxBridge` is gone in 0.87.** The WatermelonDB and onnxruntime patches read `runtime` / `jsCallInvoker` through a local protocol (llama.rn's `RNLlamaBridgeRuntimeAccess` shape), which bridgeless `RCTBridgeProxy` implements. A failed install is silent (WatermelonDB goes `asynchronous`, TTS quiet). On each RN bump, grep `node_modules/react-native/React/Base/RCTBridgeProxy.mm` (shipped even with the prebuilt core) for `- (void *)runtime` and the `jsCallInvoker` getter: `-runtime` is in no header and `jsCallInvoker` only in `RCTBridgeProxy+Cxx.h`, so a removal fails only at runtime. Android WatermelonDB already runs `asynchronous` (one "JSI SQLiteAdapter not available" per launch, `main` too).
- **Legacy-arch modules ride the interop layer** (pending PR: `react-native-tcp-socket`). Only a device build proves their events still arrive after an RN bump: re-run the local API server's on-device check (`local-api-server.md`, Verification) and the audit below over its sources. `NSLocalNetworkUsageDescription` covers serving the model as well as connecting to remote servers.
- **Audit `node_modules` on every RN or native-library bump** (these breaks are silent): `absoluteFillObject` / unguarded `InteractionManager` in runtime JS; `react-native/Libraries/*` imports that no longer resolve (calibrate with a known-missing path); `RCTCxxBridge` in compiled iOS sources outside a legacy-arch guard, version guard or off flag (`RNS_USE_CXXBRIDGE`; VisionCamera FrameProcessors, on once `react-native-worklets-core` is installed).
- **The Hermes Babel profile skips class-fields transforms**, breaking WatermelonDB's legacy decorators. The override stays scoped to the models: globally it runs before the TypeScript plugin and turns type-only fields into `undefined` own properties that `makeAutoObservable` observes. It matches the `src/database/models` path, so keep models there: a decorated model elsewhere builds, then throws "Decorating class property failed" on first read.
- **RN 0.87's Android API breaks at compile time, in `:app` and libraries alike.** `react-android` carries Kotlin metadata 2.2, so `currentActivity` as a property no longer compiles (use `reactApplicationContext.currentActivity`; speech ≥ 2.5.2, picker ≥ 11); `DisplayMetricsHolder` lost window metrics (`MainActivity` reads the Application context's); a bare `this` in `DefaultReactNativeHost(this)` hits `ReactNativeHost`'s private companion. The Gradle plugin no longer enables `buildConfig` for every library (WatermelonDB patch); AGP 9 rejects `proguard-android.txt`.
