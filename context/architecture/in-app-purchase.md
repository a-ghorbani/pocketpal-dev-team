# In-App Purchase

## Purpose

Buying a paid PalsHub Pal through the platform store (StoreKit 2 on iOS, Google Play Billing on Android), turning the store transaction into an installed Pal, and keeping that ownership correct across crashes, restarts, refunds, withdrawals, opt-in creator updates, restore and sign-in. Not covered: what a Pal is and how a PalsHub Pal becomes a local Pal (`pals-and-talents.md`, Contracts and invariants, "PalsHub install path"), the Pals grid (`pals-screen.md`), model selection (`model-loading.md`), and the account library sync (`SyncService`).

## How it works

`App.tsx` calls `purchaseStore.start()`: it subscribes the store's transaction listener and an `AppState → active` handler, waits for `palStore.ready`, then runs `recover()`. Recovery re-inits billing (availability), drains the grant queue, drives every store transaction whose record is still open through `processTransaction`, drops stale pending records, then calls refresh, but only when the entitlement query succeeded (`storePort.queryOk`, captured right after the query because later link and install queries overwrite it).

**Buy** (footer): `buy_tap` event → binding when signed in → `store.purchase` → outcome. `purchased` goes to `processTransaction`; `pending` writes `pending_payment`; `already_owned` runs `installOwned` (current entitlements, no sync); `cancelled` / `error` send their event and close the sheet.

**processTransaction** is serialized per product and branches on the record's current status. Open (missing, `pending_payment`, `unlocking`): write `unlocking`, verify, then write the outcome and finish (see the acknowledgement contract). Settled records never re-open; they are re-verified only when the caller asks (`settledVerify`: listener, `installOwned`, restore), for refunds, withdrawals and newer creator versions. A grant is installed by `drainQueue` through `palStore.installOwnedPal`, which moves the record to `active`: a new row gets the full version; an existing row is adopted unwritten, and a grant differing from its prior `applied` becomes the pending update. The grant is one `GrantedVersion` (`{pal, content, contentVersion?, changeNote?}`, the `PendingUpdate` shape with an optional version), so it becomes the pending update unchanged, change note included.

**Creator updates are opt-in.** `offerUpdate` stores a newer verify/refresh version as `pendingUpdate` (an empty diff against `applied` just advances `contentVersion`). The card badge opens the sheet; Update → Confirm runs `applyUpdate`, which writes `changedCreatorFields(applied, pending.content)` through `palStore.applyCreatorUpdate` and advances `applied`. `applyCreatorUpdate` reports `{thumbnailFailed}`; on a failed thumbnail download `applied` keeps the old `thumbnail_url` (the other fields advance), so the next update still sees it as changed and retries it.

```
(none) ─tx pending→ pending_payment ─tx purchased→ unlocking ─verify active→ granted ─install→ active
unlocking ─verify fail / unavailable→ unlocking (backoff)      ─pending→ pending_payment
          ─unfulfillable→ unfulfillable   ─revoked→ removed (tombstone)   ─invalid→ record deleted
          ─invalid + support code→ held_invalid ─Restore/Owned re-verify active→ granted (or revoked/removed/unfulfillable)
held_invalid ─Android: successful query without the product→ record deleted (Buy returns)
unlocking | granted | active ─removed→ unfulfillable (terminal; local row deleted unless the library lists it; applied cleared)
granted | active ─revoked→ removed (pending and grant cleared; applied kept only if the signed-in library keeps the local row)
removed ─verify active→ granted (revived; no applied means the full version installs)
active ─newer creator version→ active + pendingUpdate ─Update confirmed→ active
```

Precedence: `unfulfillable` > `removed` tombstone > the rest; refresh skips both.

The footer phase is `flowFor(palId)`: the record status plus transient `paying`, `ready` (active reached in this sheet session), `invalid` and `restore_needed`.

## Contracts and invariants

- **One writer.** `PurchaseStore` alone writes the ledger (`purchase-ledger` in AsyncStorage, `{version: 1, records}`), availability and the product cache. Writes are full-document, awaited, and serialized through one queue.
- **Status only moves forward.** No event returns a settled record (`granted | active | unfulfillable | removed`) to an open one, and a failed or `unavailable` verify never changes a settled record.
- **Persist before finish.** The outcome (`granted`, `unfulfillable`, tombstone, or the `invalid` delete) is written before `store.finish` (`finishTransaction`, `isConsumable: false`, never a consume).
- **The app acknowledges delivered Android purchases.** On Android, `finishTransaction` is the acknowledgement, so it is called only for a delivered purchase: after a verify `active` (grant written), after a revived tombstone's grant, and on recovery for an `active`/`granted` record whose purchase Play reports unacknowledged (`StoreTransaction.unfinished` = purchased and not `isAcknowledgedAndroid`, so `recover` re-drives it). Never for `removed`, `unfulfillable`, `revoked` or `invalid` (Google auto-refunds an unacknowledged purchase after 3 days) nor for pending or a failed/`unavailable` verify. iOS finishes every settled outcome as before. `finishedTxs` records a transaction only after its finish succeeded. On iOS it lives for the session; on Android it is cleared at the start of every `recover`/`restore` store query, so it only stops the Buy + listener double delivery within one snapshot. Across queries Play's own flag (`unfinished`) is the dedupe: an acknowledge that failed, or resolved without sticking, is retried on the next query, and a purchase the query reports acknowledged is never finished again.
- **Only Buy starts a payment.** Recovery, restore, `installOwned` and already-owned never call `store.purchase`.
- **Only an explicit server `revoked | removed` removes ownership**, from a verify or a refresh that parsed: `revoked` (refund) → tombstone, `removed` (operator withdrawal) → `unfulfillable` (`withdraw`). A moderation-rejected Pal still verifies `active` and is delivered. Moderation rejection, unpublishing, a failed refresh, a Pal missing from a list, sign-out or a library change removes nothing, and the server revokes a known entry only on its own recorded revocation for that entry's `purchase_ref`. Removal keeps the local Pal when the signed-in library lists it.
- **No automatic path changes an installed store-owned Pal.** Only `applyUpdate` after a user Confirm writes an existing `local_pals` row; a withdrawal only deletes it.
- **The diff depends only on two creator versions**: raw projections (`projectCreatorContent`, taken before `transformApiPal` fills defaults), normalised on both sides at compare time. `creatorContent.ts` imports no store, settings or defaults. No `applied` means every field changed.
- **Declining costs nothing.** Nothing gates chat, model load or editing on `pendingUpdate`; the badge is one passive label (`updateAvailable`: active, pending, installed) with no count, escalation, timer or modal.
- **`applyUpdate` is bound to the shown version**, serialized per product, and a no-op otherwise. The footer holds the confirming `contentVersion`, not a flag, so a newer pending version replaces the confirm step with its own prompt. `known.content_version` is `max(applied, pendingUpdate)` version: a freshness hint only (never entitlement), so a declined update is not re-sent on every refresh.
- **A failed store query never refreshes.** When the entitlement query failed, recovery skips refresh and `markLedgerWritable`; `dropStalePending` takes the same captured flag.
- **Refresh sends `known = {pal_id: {content_version, purchase_ref}}`.** `purchase_ref` is the `supportCode` of the most recent verify `active` applied to the record (`writeGrant`, or the settled re-verify of an `active` record), replacing any older code, never a fallback to one. An `active` without a code still grants and acknowledges, logs one warning naming only the pal id, and leaves the code absent, so the record stays out of `known`. Only `active` records with a support code go in; it is never derived from a token, JWS or transaction id. The server answers a missing ref or the old `{pal_id: version}` shape with a 400, which the app treats as a failed refresh.
- **`needsLink`** (Settings link row): signed in, some `active` record is not linked to this user; signed out, some `active` record has no `linkedUserId` at all.
- **Legacy installs are untouchable.** A local paid Pal with `is_owned` and no ledger record (a web purchase) is owned, and the IAP flow never refreshes, mutates or deletes it.
- **Buy renders only when** billing is `ready`, `iap_enabled[Platform.OS]` is true, the store returned a product in this storefront, and the Pal is not owned and has no ledger record of any status. Otherwise nothing renders: no disabled or error variant. The price string comes only from the store.
- **Wire names live in `iapWire.ts`.** Verify results and refresh `changed` carry `content` and `changeNote` (optional `change_note`; a bad value is dropped, never a parse failure) beside `pal`. An unparseable body is a failed verify, never a grant. An `active` result without a system prompt is treated as failed. `unavailable` is retryable; `invalid` is terminal for that transaction this session (`invalidTxIds`, skipped by `recover`). An `invalid` with a support code is a real store transaction the server cannot grant: it becomes `held_invalid` (settled; hides Buy, shows `heldInvalid` plus the code in the footer and Settings, with a Restore button), re-verified only by an `install` path (Restore, Owned), never by the listener or recovery, and never finished on Android. On Android a successful `recover`/`restore` query that lists nothing for its product deletes it (Buy returns); a failed query never does, and only holds present before the query are candidates. Android refresh `revoked`/`removed` never touches it (a tombstone would hide Buy and escape that clear). iOS is unchanged: no query clears it, and a later refresh verdict can still tombstone or withdraw it.
- **Request limits.** Verify sends at most 10 transactions (Android) or 50 (iOS) per request and refresh at most 200 `known` entries; `iapApi` chunks and merges. Within one merged response a revocation wins only for the same purchase (same `support_code`): `revocationWins` turns that `active` into the revocation, and refresh drops a `changed` pal it also revokes (one `purchase_ref` per pal). A different purchase of the Pal that is `active` keeps it owned: `PurchaseStore.verify` takes the first `active` result, so a refunded sibling purchase never removes a re-purchase. Each refresh chunk carries the full transaction list.
- **Account-free calls carry no `Authorization`:** verify, refresh and events. Link and binding do. `X-IAP-Capable: 1` and `X-Client-Platform` always travel together, on every PalsHub request (`apiRequest`, `iapApi`, `palEvents`).
- **Tokens, JWS and binding values are never persisted or logged.** The ledger stores transaction ids and support codes (shown verbatim); proofs are re-read from the store.
- **Automatic paths never prompt for an Apple ID.** `recover` and `installOwned` use current entitlements; only `restore()` calls `store.sync()`.
- **`FakeStore` and the API-base override exist only under `__E2E__`.** Their markers (`IAP_FAKE_STORE`, `IAP_API_BASE_OVERRIDE`) are in the `ci.yml` prod-bundle grep.

## Traps and decisions

- **The library is event-based.** `requestPurchase` resolves before the outcome; `NativeStore.purchase` waits for the first matching update or error event. The same purchase also reaches the global listener, so every purchase is processed twice; per-product serialization makes the second a settled no-op (it may re-verify, which is idempotent).
- **iOS dedupes transaction events per id.** A re-buy of a delivered transaction would never emit to a deduping listener and `paying` would hang, so the purchase-scoped listener passes `dedupeTransactionIOS: false`; the global `onTransaction` listener keeps deduping, because replays would re-verify settled records. As a backstop, 5 s after `requestPurchase` resolves with no event, iOS settles from the unfinished and entitlement lists for the product (same pending / 60 s already-owned mapping), else a non-downgrade `error`; recovery still picks up a real transaction.
- **Android excludes Compose UI and Compose runtime, never Gson** (`android/app/build.gradle`, app variant classpaths only). openiap-google's `OpenIapModule` uses Gson; excluding it breaks billing at runtime (no restore row, no Buy) while builds and FakeStore e2e stay green. Compose is used only by the unreferenced `IapContext*` (plus binary-retention `StabilityInferred` annotations). Only a real-store build proves a classpath exclude.
- **iOS already-owned is inferred.** StoreKit returns success with the original transaction; a transaction dated more than 60 s before the request is read as `already_owned`. A misread is harmless: `installOwned` re-verifies through the same pipeline.
- **One ledger in AsyncStorage, not WatermelonDB tables.** `mobx-persist-store` writes cannot be awaited, and the persist-before-finish rule needs an awaited write.
- **Tombstones, not deletions.** The store keeps listing a refunded product; a `removed` record stops `recover` re-driving it and hides Buy until a later explicit `active` verify revives it.
- **Stale pending differs by platform.** Play lists pending purchases, so Android drops a `pending_payment` record at once once a successful query no longer lists it. A declined Ask to Buy emits nothing on iOS, so the record ages out after 72 h, or at once on Restore. `dropStalePending` also clears an Android `held_invalid` record by the same test (Google auto-refunds an unacknowledged purchase, then Play stops listing it); held records never reach the iOS age/`force` branch.
- **Refresh never installs.** It offers updates only for installed `active` Pals; a deleted Pal stays deleted until Owned or Restore re-grants the full version.
- **A withdrawal is terminal** so the sheet and Settings keep its copy; it also blocks re-buying on that device (`canBuy` requires no record).
- **Undeliverable copy depends on platform and delivery** (`utils/undeliverableCopy.ts`, footer and Settings, always followed by the support code). iOS: `noLongerAvailable`. Android, never delivered (verify-time `removed`/`unfulfillable`): `notCompleted` (Google's automatic refund; never "refunded"). Android, withdrawn after delivery (`withdrawnAfterDelivery`, set when `withdraw` hits an `active`/`granted` record): `withdrawnRefunding` (the operator refunds). A changed meaning gets a new key, so stale translations never carry the old one.
- **Closing the sheet never cancels a paid flow.** State is in the ledger; reopening shows the current phase.
- **Availability downgrade is per session.** A store refusal (`developer-error`, `billing-unavailable`, `item-unavailable`, …) sets `unavailable` until relaunch. A sideloaded build Play refuses shows no Buy rather than errors.
- **Binding never blocks a purchase.** A slow or failing binding request goes ahead unbound after 2 s; a signed-in purchase links silently after `active`, and a signed-out buyer gets one dismissable sign-in prompt that links on sign-in (`requestLink` + an `isAuthenticated` reaction). A 409 keeps the Pal and shows "linked to another account".
- **Retries are in memory.** Backoff is 2, 4, 8, 16, 32 s, then every 60 s while foregrounded, paused in the background. After a restart, `recover` re-drives open records from the store's own list, and Retry runs at once.
- **iOS needs glog's textual module map.** Under `use_frameworks!`, NitroModules' Swift C++ interop imports the React headers as Clang modules, and glog's `logging.h` includes `log_severity.h` / `vlog_is_on.h` inside `namespace google`, which is illegal as a module import. `ios/Podfile` `post_install` points only the glog target at a module map that marks those two headers textual. Removing it breaks the iOS build with "could not build Objective-C module 'NitroModules'".
- **Android e2e cannot use the deep-link host.** The Android Linking listener routes only the benchmark URL, so specs drive the FakeStore through `IapAdapter`; iOS uses `pocketpal://iap?cmd=…`. The FakeStore persists its state (including the API base) under `e2e.fakeStore`, and `start()` awaits `fakeStore.restore()` before the first `init()`.
