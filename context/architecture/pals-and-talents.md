# Pals & Talents

## Purpose

What a Pal carries for tool use (`pact`, `greeting`), what a Talent is (engine plus optional UI), how a Pal opts into tools, and the execution boundary engines respect, including the search talents' trust rules. Elsewhere: the agent loop (`agent-runner.md`), rendering and persistence of tool outcomes (`chat-flow.md`), search settings and consent UI (`settings.md`).

## How it works

`registerDefaultTalents()` fills `talentRegistry` at `PalStore` init and lazily from `deriveToolSchemas` / `collectSystemPromptFragments`. `TalentSurface` calls `registerDefaultTalentUIs()` at module load.

`ChatSessionStore.resolveCompletionSettings` layers defaults, then global settings, then Pal `completionSettings`. It then sets `tools = deriveToolSchemas(pact.talents names)` when that list is non-empty. When the session uses `settingsSource === 'custom'`, the session's params replace the result but the PACT `tools` are re-applied.

`useChatSession.prepareCompletion` then:
- collects talent `systemPromptFragment`s for the session's tool names;
- folds them into one system message with `assembleMessages`;
- reseeds the `read_url` allowlist with `seedReadUrlAllowlist`.

The run dispatches through `talentLookup` with `allowedTalentNames` from `pact.talents` (see `agent-runner.md`). `TalentSurface` renders each settled call: `ToolErrorBlock` for an error, else a registered `TalentUI.renderResult` (plus `ToolMetricsFooter` when `call.metrics` is set), else `ToolUsedChip` with metrics inline. `PendingIndicator` covers calls with no outcome yet.

## Contracts and invariants

- **PACT is the single opt-in.** Advertised tools are `deriveToolSchemas(pact.talents.map(t => t.name))`. The runner dispatches only names in that same list. Engines are global, and there is no Pal-id coupling (`TalentRegistry`).
- **One name, three places.** `TalentEngine.name` is the tool name, the `talentUIRegistry` key, and the `TalentRef.name`. `register()` silently replaces a same-name entry, and nothing warns about collisions. *(PR #921 only)* That is why a non-builtin source never registers a name it does not already own: built-ins claim theirs first, and the bridge skips any name already taken, so a user tool can never shadow `calculate`.
- *(PR #921 only)* **A source owns the names it registers.** `attachTalentSource` runs one fire-immediately MobX reaction over `source.engines()`; each run unregisters the owned names no longer produced, then registers the current ones. It returns a disposer that stops the reaction and gives up every owned name, and `resetRegisteredFlag()` calls it — without that, a test reset stacks a second reaction and leaves a stale owned-name set. `TalentRegistry.unregister(name)` exists for this.
- *(PR #921 only)* **Import direction is one-way:** `talents/index.ts` → `CustomToolStore` → the custom-tool validator → `builtinTalentNames.ts`, a leaf with no imports. The store and the validator never import `services/talents/index` or `store/index`, which keeps the graph acyclic under Babel's CommonJS interop.
- **`TalentSection` lists whatever is registered,** re-read each time the sheet mounts, so any registered engine (under PR #921, a custom tool) appears with no edit: `title` falls back to the engine name and the description to `toToolDefinition().function.description` when l10n has no entry.
- **Unknown PACT names are dropped silently.** `deriveToolSchemas` filters by what is registered, so a Pal naming a talent this build lacks runs as plain chat (forward-compat for PalsHub Pals).
- **Custom session settings never strip PACT tools.** `resolveCompletionSettings` re-applies them after the `custom` layer. Generation params and tool availability are separate concerns.
- **Engine boundary.** `execute(args) → Promise<TalentResult>` never touches React, MobX or stores. Network and Keychain are allowed; store state reaches search engines only through the `SearchAccess` built in `createSearchAccess`. `talents/index.ts` is the only talents file importing a store (PR #921 adds `CustomToolStore` there, behind `createCustomToolAccess`). Output leaves only as a `TalentResult`, and `summary` is what the model sees. `execute` takes an optional second argument, a `{signal}` context, which every engine gets whenever the run has a signal (`agent-runner.md`). *(PR #921 only)* That PR passed `ctx` only to engines declaring `timeoutMs`; on rebase it must keep passing it to every engine.
- **Stop reads `cancelled`, never `timed out`.** Search engines forward `ctx.signal` through `SearchProvider.search/read(…, signal?)` and `readWithDefaultReader` as `init.signal`. `withTimeout` aborts its own controller on the first of its timer or that signal (a listener: RN's `AbortSignal` lacks `any`), classifies by which fired, and removes the listener in `finally`, since the run signal outlives many calls. A cancelled search caches and allowlists nothing.
- **At most one system message, and it comes first.** Talent fragments are folded into the Pal prompt by `assembleMessages`, joined with a blank line, Pal prompt first. A talent never emits its own system message, and strict chat templates `raise_exception` on a second one. Attached documents go in user messages only (`documents.md`). The stored Pal prompt is never modified. `__DEV__` logs a violation, and `useChatSession` / `systemPromptResolver` tests assert exactly one.
- **Search consent is load-bearing at execution.** Both search engines return an error result unless `canSearch()` (consent and a configured key); the Settings disclosure is not the only gate.
- **`read_url` order of checks.** A plain `http(s)` URL with no userinfo, `canSearch`, the allowlist; then fetch the fragment-stripped canonical URL through the provider's native `read` (Exa, Firecrawl) or else `readWithDefaultReader` (`r.jina.ai`, which the consent disclosure names). The lookup is `matchReadUrl` (the barrel's `isReadUrlAllowed` is its boolean wrapper); the fetch is the matched exact entry, or the request's canonical URL (fragment dropped, host case folded, no userinfo) when its host is a site the user named. A successful read returns the URLs written out in its budgeted page text as a capped `links` field (first 100).
- **Allowlist trust sources.** Entries come only from user-written message text and from persisted `step.toolOutcomes` (seeded at run start), plus live additions (`WebSearchEngine` calls `allowReadUrls`; a successful `read_url` adds its `links`). Assistant text, tool-message text, attached document text, document excerpts and retrieval queries never count: the seed takes the typed user texts, not assembled content (pending PR). A future `search_documents` talent's result is tool output and goes through `wrapUntrusted`. Canonicalization drops the fragment and lowercases ASCII host letters. Only `seedReadUrlAllowlist` / `isReadUrlAllowed` are exported from the talents barrel. Two kinds of entry. **User sites**: every host in user-written text, from scheme URLs or bare hosts (user text is split into words at whitespace, quotes, brackets and every non-ASCII character except Latin (including combining marks and Vietnamese), Greek, Cyrillic and Armenian letters, with the fullwidth `＠` and small `﹫` read as `@`; a word seeds the host at its start, after an optional `http(s)://` and before any `/?#`, when that host is ASCII labels with a 2–63-letter TLD (an IPv4 only after a scheme), splitting on `:`, `,`, `|` and other sub-delimiters and ignoring trailing dots, and seeds nothing if an `@` precedes the path; non-ASCII hosts typed by the user do not seed and are reached through search hits or page links), allows any scheme, port, path and query on that host or its `www.` form, never subdomains; only the seed writes them. **Exact entries**: web_search hit URLs and `read_url` result `links` (persisted and live; snippets, hyperlink targets and text past the budget never count, and `summary` is never parsed); extraction trims trailing `.,;:!?`, `…` and CJK/fullwidth closing punctuation, and a trailing `)` only while unbalanced (linear scan; page text is hostile); the match key is host minus one `www.`, port, path minus one trailing `/`, exact query, scheme ignored, and a lookup returns the stored string, so a key collision can only return another allowlisted string and lookups never write. Entries with userinfo are never stored, and a lookup never returns userinfo. When both www and bare forms are stored, either stored entry may be fetched. Accepted residuals: a user-named site, its open redirects, or its reflected input lets the model send data onward; pasted text counts as user text, and inside a user-typed URL, text after a bracket, quote or non-ASCII character starts a new word that can seed a host; a purpose-built site can leak through a chain of link choices.
- **All retrieved web text is wrapped by `wrapUntrusted`** before it reaches the model: the search menu and the page body. Literal marker strings in the page are neutralised.
- **The search token ceiling is charged against the rendered bullet.** `budgetHits` takes the model-facing renderer; raw fields under-count markdown and leak past the cap. Engines read their own `recommendedContextTokens` as that ceiling. `toPlainText` leaves http(s) URL spans intact when stripping emphasis/heading markers (a trailing emphasis run excepted, so a URL genuinely ending in `_`, `*`, `` ` `` or `~` loses it), so URLs in page text and in hit titles/snippets survive budgeting; markdown link targets and `<url>` autolinks are still dropped. `URL_PATTERN` in `searchBudget.ts` is the one URL pattern, shared with the allowlist; it is a `/g` instance, so use it only with `match`, `replace` and `.source`.
- **Outside engines, `recommendedContextTokens` is read only by `usePalLoadHint` and `BannerRow.deriveHeavyTalentName`;** it never moves a banner threshold.
- **`web_search` returns `{type:'search'}`,** with structured `results[]` for `WebSearchTalentUI` and the wrapped menu as `summary`. The UI never parses model-facing text.
- **PalsHub install path.** Every PalsHub Pal enters `local_pals` through `PalStore.insertPalsHubPalOnce`: a per-`palshub_id` promise chain that checks the DB (not the in-memory `pals`) and returns an existing row instead of inserting a second one. `downloadPalsHubPal` (library, with its ownership check) and `installOwnedPal` (store purchases, no ownership check, `in-app-purchase.md`) both use it; `PalStore.ready` is the `initialize()` promise that installs wait on.
- **A store purchase never writes an empty prompt.** `installOwnedPal` throws without `system_prompt`, and `applyCreatorUpdate` skips the prompt fields when the new content has none.
- **A store-owned Pal changes only on Update.** It overwrites the creator fields changed since the last-applied snapshot (ledger `applied`, `in-app-purchase.md`), including user edits there, and clears removed ones; unchanged fields keep user edits. `applyCreatorUpdate` gets the field set and writes only those columns, with values from `createLocalPalFromPalsHub` (the diff never depends on that conversion): the prompt group (`systemPrompt`, `originalSystemPrompt` (`''` when not templated), `parameterSchema`, `parameters`, keeping user `parameters` for keys the new schema still has), `defaultModel` (`null` when removed), generation settings (`null`), `pact` (`{talents: []}`), `greeting` (`null`), `description` (`''`), categories and tags (`[]`), creator info, protection level, name. The thumbnail is re-downloaded only when the creator supplies one and is never cleared. The model is resolved only when it changed.
- **The editor always writes `necessity: 'required'`** (`PalSheet.onSubmit`). `'optional'` arrives only through import or PalsHub (wire `required` maps strictly, `=== true`, in `PalStore.createLocalPalFromPalsHub`). Nothing enforces `necessity`, so a future gate must default to not blocking. `onSubmit` always passes `pact` (possibly `{talents: []}`) because `PalRepository` skips `undefined` updates.

## Traps and decisions

- **`CalculateEngine` pins `expr-eval` to `{allowMemberAccess: false}`.** This blocks the `(0).constructor.constructor(...)` escape on non-Hermes runtimes. Engine purity is not sandbox safety: an engine that wraps an untrusted-input parser must pick the locked-down configuration itself.
- *(PR #921 only)* **Component tests and the registration bridge see two different store instances.** `jest/setup.ts` replaces the `src/store` barrel with mocks, while `services/talents/index.ts` deep-imports `store/CustomToolStore`, so the bridge reads the real store even where a component test has mocked the barrel. The deep import is deliberate — the barrel would close a cycle (`store/index` → `ChatSessionStore` → `services/talents/index`) — and it follows this file's own precedent, which deep-imports `SearchProviderStore` the same way. The consequence is that the mock store's `okTools` must reproduce the real getter's filtering rather than return every tool; a test now pins that, because nothing else read the mock's value and the drift was invisible.
- **Talent-internal mutable state assumes one agent run at a time.** This covers the search-hit cache and the `read_url` allowlist. If concurrent runs ever land, thread a run-scoped context through `execute`.
- **Result count comes from settings, not a tool parameter**, so the model cannot inflate injected tokens. Defaults are `brave` with 5 results (range 1–8, `SearchProviderStore`). Brave with 5 results grounded small on-device models best.
- **Search errors steer the model in-band.** Every failure is an error result: no results says to shorten the query, a blocked `read_url` to use a site the user named, a URL from a web_search result or a page it read.
- **A provider's malformed-response check uses only fields its success envelope always carries.** These are Brave `type: "search"`, Firecrawl `success: true` plus a `data` object, and the `results` array for Tavily, Exa search and read, and Parallel. A failed check throws the fixed `unexpected response` with no body content. Never require a field that a zero-hit response leaves out or empties: live, a zero-hit Brave body has no `web` key and a zero-hit Firecrawl body has `data.web: []`. Requiring either would turn every no-hit search into an error instead of the "shorten the query" result.
- **The RN `URL` polyfill is not Node's `URL`.** On device (`react-native-url-polyfill/auto`) hosts are neither lowercased nor punycoded, and `www.1.2.3.4` / `www.0x7f` parse as domains; Jest's Node `URL` hides all of this. That is why the allowlist folds `[A-Z]` itself; the odd `www.` IP forms are harmless because a lookup returns only a stored entry or a URL on a host the user typed. User-text word splitting uses explicit code-point ranges because Hermes has no `\p{}` escapes. Host-sensitive allowlist tests also run with `globalThis.URL` swapped for the polyfill's (`jest/urlImplementations.ts`), which needs `react-native-url-polyfill` in `transformIgnorePatterns` because it ships untransformed ESM.
- **Grounding lives on the engine.** `WebSearchEngine.systemPromptFragment` adds today's date, search-first, a tool budget of `maxToolTurns − 1`, answer-from-results-and-cite-URLs, and "say so rather than guess"; it mentions `read_url` only when that talent is active. `read_url` has no fragment, so a Pal with only `read_url` gets no grounding.
- **The hit cache key excludes the BYOK key** (a secret must never be a map key), so invalidation is explicit: `SearchProviderStore` calls `resetSearchCache` on provider, key and consent changes. A new store setter that affects results must do the same.
- **The greeting is UI-only and gated on a loaded model.** It is never persisted or sent to the model. `ChatView` renders the greeting bubble and suggested prompts only when `modelStore.activeModelId` is set.
- **`TalentUI.renderPending` is deprecated and never called.** `PendingIndicator` owns in-flight UX. New UIs must not implement it.
- **Two registries rather than one map,** so text-only talents (`calculate`, `datetime`, `read_url`) need no UI plumbing and engine consumers never load the UI tree.
- **`isSystemPromptChanged` is not an edit signal.** No editor path sets it; store-owned updates don't need one, because Update overwrites changed creator fields regardless of edits.
- **Clearing needs an explicit value.** `PalRepository.updatePal` skips `undefined`; `null` (allowed by `PalUpdate` for `greeting`, `defaultModel`, `rawPalshubGenerationSettings`) stores NULL on those optional columns and reads back as `undefined`.
- **Edits to `pact` apply on the next `resolveCompletionSettings`.** An in-flight run keeps the `tools` / markers it captured at submit.
