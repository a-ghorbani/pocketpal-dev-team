# Sheets

*(pending PR #979: everything below on keyboard lift, `topInset`, snap-point resolution and the multi-window opt-out; on main, sheet inputs do not lift the sheet)*

## Purpose

The shared `Sheet` (`src/components/Sheet`, a `@gorhom/bottom-sheet` `BottomSheetModal`) and how its inputs behave with the keyboard: input registration, the multi-window opt-out, the status-bar clamp, percentage snap points, and the scroll view's focused-input reveal. Not covered: what any one sheet does (each flow doc owns its sheets, e.g. `settings.md`, `remote-servers.md`), and the DS sheet in `src/components/ui/Sheet` (redesign layer; it has neither `topInset` nor snap-point resolution, and no callers).

## How it works

Focusing a registered input sets gorhom's keyboard `target`; the following keyboard `SHOWN` lifts the sheet (`keyboardBehavior` default `interactive`). If the sheet plus keyboard fits below `topInset`, the whole sheet translates and nothing scrolls. Otherwise gorhom clamps the sheet top at `topInset` and shrinks the content; `Sheet.ScrollView` sees a smaller `onLayout` height, and on the next frame measures the focused input against its inner view and scrolls by the minimum delta that puts the input's bottom edge inside the viewport (`animated: false`). Content size changes (a growing multiline input) schedule the same reveal. Keyboard hide restores the snap point: gorhom's `restore` for an unclamped lift, `useClampedLiftRestore` for a clamped one.

When the app window is smaller than the screen (Android split screen or freeform, iPad Split View, Stage Manager or Slide Over, desktop mode), `SheetAwareNativeInput` clears the target its own focus just set, so the `SHOWN` finds no target and the sheet stays at its window rest, as on main. The gate is read at every focus, never latched.

## Contracts and invariants

- **Rest geometry.** With the keyboard closed, every sheet's top edge is where it was before `topInset` existed: `'<p>%'` resolves to `p/100 ×` `useSafeAreaFrame().height`, the box gorhom's modal host fills, capped at `fullHeightSnapPoint` (`snapPoints.ts`); a frame change (rotation, or a window resize in split screen, freeform, Split View, Stage Manager or Slide Over) re-resolves the points and the `maxDynamicContentSize` cap, as gorhom's own percentages did on main. Numeric points, `displayFullHeight` and dynamic sizing pass through. `snapPoints`, `onChange` and `onAnimate` are destructured out of the props before the `{...props}` spread, so the spread cannot reintroduce the raw value or bypass the wrapped handlers.
- **Focused input visible.** In a full-screen sheet, the focused input is fully above the keyboard; a multiline input taller than the viewport keeps its bottom edge visible while typing at the end.
- **Actions reachable.** When lifted, `Sheet.Actions` sits above the keyboard.
- **Status bar.** A lifted sheet never goes above `insets.top` (`topInset` in `Sheet.tsx`).
- **Every sheet input is a `BottomSheetTextInput`; its focus registers in full screen only.** Inside a `Sheet`, inputs are the shared `TextInput` (sheet-aware by default), `Sheet.TextInput`, or Paper `TextInput` with `render={renderSheetAwareInput}`, all of which render `SheetAwareNativeInput`. Full screen, the wrapper adds no write and no dismiss, so a focus registers and lifts. A focus that begins windowed never leaves the target set past the UI batch that set it, so it never lifts and never blanks; the one exception is a focus begun full screen that survives a height-only window change (Traps). A raw RN `TextInput` in a sheet never lifts it.
- **A flip while focused dismisses the keyboard.** A flip is a render where the gate and the frame width both changed. The focused sheet input calls `Keyboard.dismiss()` in either direction; gorhom's blur clears its target and `keyboardDidHide` restores the sheet to window rest. Nothing else dismisses, so a keyboard-only frame change never does, and no input lifts with numbers from the previous window. Unfocused inputs do nothing; their next focus reads the new gate.
- **testIDs stay on the native field.** The registration path forwards every Paper render prop, including `testID` and `ref`, so e2e selectors and Paper's focus/blur/clear are unchanged. Nothing remounts at a flip, so text, refs and selection survive it.
- **No lift without own focus.** Detection is per sheet context; a stacked lower sheet never moves for an input in the sheet above. The windowed clear is tag-checked, so it never removes another input's target. The reveal's `measureLayout` fails for an input outside the scroll view, and failure is a no-op.
- **One engine, no band.** gorhom is the only keyboard engine in a sheet. `Sheet.ScrollView` adds no padding or spacer, never scrolls an input that is already inside the viewport, and never scrolls past the content end (`revealOffset.ts`).

## Traps and decisions

- **Plain inputs never lift a sheet.** gorhom caches a `SHOWN` that arrives with no `target` and does nothing; only `BottomSheetTextInput`'s focus sets the target. Paper renders RN's `TextInput`, so before registration both key sheets stayed put under the keyboard.
- **Paper calls `render` as a plain function** inside its own component. Detection needs its own fiber, so `render` is `renderSheetAwareInput` returning `<SheetAwareNativeInput/>`, never the component itself. A component that renders `<Sheet>` is outside its own sheet context, which is why detection lives at the input's mount site. The gate hooks live in an inner in-sheet component, so Paper inputs outside sheets subscribe to nothing.
- **`interactive` clamps to the container top.** Without `topInset` a tall sheet would be clamped under the status bar (the reason `SearchableSelectSheet` still opts into `extend`; dropping that override is optional now, not done). Windowed, its `extend` shrink is gone with the lift; its search field sits at the sheet top, so it stays visible.
- **A clamped lift never restores on its own (gorhom 5.2.8).** `animateToPosition` records a lift it cannot match to a detent with `highestDetentPosition` (pixels) as the index, so `restore` reads `detents[<pixels>]`, gets `undefined` and leaves the sheet at `topInset`. `useClampedLiftRestore` tracks the target index from `onAnimate` (animation start, `-1` for a close) and `onChange` (completion); one frame after `keyboardDidHide` it re-checks that index against the current snap points and, only if it is still past the last detent, calls `snapToIndex(highest)`, the detent gorhom restores to when unclamped. Checking inside the frame means a close or snap that starts before it (swipe or X while lifted) is not undone; snap points are read from a ref so a parent re-render does not cancel the pending frame. Residual risk: a close whose `runOnJS` `onAnimate` reaches JS after the frame. Measured on Xiaomi (Android 16): 50/60/70/80% and full-height sheets back at rest y with back and IME done. Drop the hook when gorhom indexes the clamped lift correctly.
- **`%` snap points resolve against the root frame because of `topInset`.** gorhom normalises percentages against its container, which `topInset` shrinks; resolving in `Sheet` keeps every percentage sheet at its old height. The frame is the `SafeAreaProvider` view's measured size, and only flex-1 wrappers sit between it and the `BottomSheetModalProvider` host, so it equals gorhom's uninset container in every window mode (full screen: 50% on a 2424 px Pixel 9 sits at y=1212). The screen height is not a substitute: in a multi-window pane it exceeds the container and every sheet at 50% or more opens at full pane height. Rotation dismissal stays keyed on screen height, so a frame-only change (divider drag, keyboard-driven resize) never dismisses the keyboard.
- **KASV inside a sheet double-corrects.** `react-native-keyboard-controller`'s `KeyboardAwareScrollView` scrolls by window geometry measured when the keyboard starts moving and appends a `keyboardHeight + 1` spacer, with no knowledge of gorhom's lift; its `scrollTo` can also be reset by gorhom's scroll lock. `Sheet.ScrollView` therefore runs no KASV, and `bottomOffset` is gone from its callers. `Dialog` is not a sheet and keeps KASV.
- **Rotation mid-lift strands the sheet (gorhom 5.2.8).** `heightWithinContainer` is computed only on keyboard show/hide, from import-time `SCREEN_HEIGHT`/`WINDOW_HEIGHT` and the container offset measured at that moment; iOS posts the rotation's keyboard show before the container re-measures, and nothing recomputes it afterwards, so the content collapses to the handle (iPad: blank sheet, header clipped). Keyboard hide recovers it, so `DismissKeyboardOnRotation` dismisses on rotation (on Android it does not always recover; see Known limitations).
- **Windowed: sheet focus stays unregistered (gorhom 5.2.8 frozen dimensions).** gorhom reads `WINDOW_HEIGHT`/`SCREEN_HEIGHT` once at import; the keyboard offset is `SCREEN_HEIGHT − kb.height − kb.screenY` and the container offset `WINDOW_HEIGHT − (pageY + height + StatusBar.currentHeight)`, measured asynchronously, and both feed the lift only on keyboard events. Widths never enter the lift (`WINDOW_WIDTH` only sizes the handle indicator).
  - A window that the OS moves when the IME opens (Android bottom split pane) blanks the sheet on focus: handle clamped, no content. A top pane, whose window stays put, happened to work. Rotated full screen is off by the frozen heights (Known limitations).
  - Gate: `|max(frame) − max(screen)| < 1 ∧ |min(frame) − min(screen)| < 1`, frame = `useSafeAreaFrame()`, screen = `Dimensions.get('screen')`, both in dp. Sorted, because frame and screen events arrive separately and a rotation transiently transposes them. 1 dp, because the frame is float dp of int px and the screen is int px / scale. Any dimension, not height only: the opt-out covers iPad Split View too, though a narrower-only window probably lifts correctly (unverified; re-enable it once verified on a device).
  - The windowed clear is a UI-runtime worklet, tag-checked, queued from the wrapper's `onFocus`. gorhom's `handleOnFocus` sets the target through `runOnUI` and then calls the wrapper's `onFocus`; `runOnUI` jobs share one FIFO flushed as one UI job before mappers run, so set and clear land back to back and a later `SHOWN` is only cached. The replaying reaction sees no target either. A JS-side `get()`/`set()` would bypass the queue and miss gorhom's pending set.
  - One native instance per mount, registration per focus. Rejected: swapping `BottomSheetTextInput` ↔ RN `TextInput` on the gate (each flip remounts the field and needs a target clear timed against ref teardown plus an `autoFocus` rule); gorhom `android_keyboardInputMode="adjustResize"` (Android only, and a sheet lifted when the window goes windowed stays stranded because the hide takes gorhom's early return).
  - Flip dismiss is width-guarded: an IME insets only the bottom edge, so it never changes frame width and can never trigger a dismiss, whatever the event order. Dismissing on windowed → full too keeps a cached `SHOWN` from replaying on the next focus. Cost: height-only changes (Android portrait split top/bottom, vertical-only freeform or Stage Manager resize) do not dismiss.
  - Misdetection costs: full screen read as windowed means no lift, never blank (Android 3-button landscape, below). A keyboard shrinking the frame would leave field-to-field focus unregistered; it was not observed.
  - Device facts (99ae699c): the root frame equals the screen in full screen on Android 16 (Xiaomi, portrait and landscape) and API 30 (OnePlus 6 with a notch, portrait in both nav modes, landscape with gesture nav). The keyboard never changes the frame (Xiaomi window unchanged with the IME shown; OnePlus 6 frame identical before, during and after the IME). Windowed on Xiaomi (split top and bottom panes, freeform) and iPad (floating and tiled windows): focus, field to field with the keyboard up (8 alternating taps, handle constant) and divider drags never lift and never blank.
  - Follow-up: patch gorhom's import-time dimensions with `patch-package` to read live window and screen sizes. That would address Known limitations 1–4 below and might remove `DismissKeyboardOnRotation` and the windowed opt-out.
- **Known limitations (shipped; gorhom 5.2.8 import-time screen/window constants unless noted).**
  1. Android, rotating with a sheet input focused (portrait lift, then rotate): the keyboard closes, but the sheet sometimes stays at the clamp top with the input not drawn (Xiaomi 3/13 at 99ae699c, 2/12 at 5e18a9cf, so it predates the opt-out). Recovery: close and reopen the sheet.
  2. iPad, full screen → windowed while focused: the keyboard dismisses and the content stays visible, but the sheet stays at its lifted top, about 240 pt above the window bottom; refocus and return don't fix it. Recovery: close and reopen. Android's full → freeform equivalent restores correctly.
  3. iPad, launched in a floating window, maximized, then focused in landscape: blank sheet, because `WINDOW_HEIGHT` froze at the small launch window. Recovery: return (keyboard hide).
  4. iPad landscape after a portrait launch: partial lift with the field behind the keyboard; a landscape launch lifts fully. OnePlus 6 showed the mirror case once (portrait focus after a landscape app start stopped short), consistent with the same constants.
  5. Android 3-button landscape (API 30, OnePlus 6): the root frame leaves out the 48 dp side nav bar, so the gate reads windowed: no lift, never blank. Accepted; widening the tolerance would admit narrow windows. Possible follow-up: tolerate a side system-bar inset.
  6. A height-only window change while focused keeps the focus's registration from the old window until a real blur: a focus begun full screen can still lift (and blank in a bottom pane) with stale numbers, and a focus begun windowed gets no lift after split → full. On Android, back hides the keyboard without blurring, so the boundary is the blur, not the keyboard closing (back then tap again still gives no lift). Recovery: a real blur, e.g. close and reopen the sheet; the next focus reads the current window.
- **Reveal trigger.** On a clamped lift, Android (Galaxy S23, Android 16) emits a single shrinking `onLayout` for the scroll view, and the reveal scroll is not reverted (the sheet is unlocked after the lift). An unclamped lift emits none, and none is needed. If a platform ever lifts without an `onLayout`, the fallback is a `useAnimatedReaction` on `useBottomSheetInternal(true)?.animatedAnimationState.value.status` going from running to stopped while the keyboard is shown, re-measuring the viewport.
- **`onScroll` is always passed** so the reveal knows the offset; gorhom then crosses to JS once per scroll frame on every `Sheet.ScrollView` (the HF list sheets included). The handler only writes a ref.

## Verification

- Unit: `src/components/Sheet/__tests__/{Sheet,snapPoints,revealOffset,SheetScrollView,screenSize}.test.ts(x)`, `src/components/TextInput/__tests__/SheetAwareNativeInput.test.tsx`, plus the author filter and select sheets in `EnhancedSearchBar.test.tsx` and `SearchableSelectSheet.test.tsx`. Jest cannot see the lift, the clamp or the reveal: the gorhom mocks are plain Views. Jest's frame mock (390×844) differs from its screen (750×1334), so the default reads as windowed and full-screen cases set the frame to the screen. The UI-batch ordering of gorhom's set and the windowed clear cannot run in Jest; only a device shows it. `Sheet.test.tsx` covers the clamped-lift snap-back from a captured `keyboardDidHide` listener; `jest/setup.ts` makes `Keyboard.addListener` return a subscription, since the automocked emitter returns none.
- By hand, keyboard open: Settings › Set Token (clamped lift: header below the status bar, input and Save visible); Settings › Internet Search › Set Key (unclamped: the whole sheet sits on the keyboard); a saved remote server's details, focusing the API key field (Save above the keyboard); About › feedback, typing past the viewport. With the keyboard closed, compare sheet top edges against main.
- By hand, windowed (Android split top and bottom panes and freeform; iPad floating and tiled windows): Set Token, Set Key, the author filter and a searchable select never lift and never blank, with the handle at window rest; tapping a second field with the keyboard up still doesn't lift; dragging the divider with a field focused never blanks.
- By hand, mode change with a field focused and the app kept active (Android `am start --windowingMode 5` / `1` on the running instance, not recents; iPad Stage Manager): full ↔ windowed closes the keyboard and blurs the field, and the next tap follows the new gate (lift in full screen, none windowed).
