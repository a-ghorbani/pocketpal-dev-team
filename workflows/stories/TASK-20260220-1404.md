### Background
Users with 15+ downloaded models cannot scroll to the bottom of model dropdown lists on shorter phones like iPhone 16 (852pt window height). The issue affects:
1. Chat page header menu model submenu (SubMenu component)
2. Pal page model selector (Selector component)
3. Benchmark page model selector (Menu component)

The user reports: "I can't get to the bottom of the model dropdown lists. It's like they were hardcoded for longer phones."

### Current State

**PaperMenu scroll height calculation** (`node_modules/react-native-paper/src/components/Menu/Menu.tsx:504-551`):
- PaperMenu detects when menu content overflows available vertical space
- Computes `scrollableMenuHeight` and wraps children in a ScrollView
- Uses `windowLayout.height` (from `Dimensions.get('window')`) as the available vertical space
- On iOS, `additionalVerticalValue` is always 0 (line 458-461)
- The calculation only subtracts `SCREEN_INDENT = 8` from the bottom edge
- **It does NOT subtract `insets.bottom`** (safe area bottom inset, ~34pt on iPhone 16 for home indicator)

**Result**: PaperMenu thinks it has 852 - 8 = 844pt of usable space, but the actual usable area is 852 - 8 - 34 = 810pt. The last ~34pt of scrollable content is hidden behind the home indicator. With 15 models at 46px each (690px total), the last 0.5-1.5 items may be unreachable depending on menu anchor position.

**Key files in current state**:
- `patches/react-native-paper+5.14.5.patch` - Existing patch for menu animation/dismissal (69 lines)
- `src/components/Menu/Menu.tsx` - PocketPal's Menu wrapper; passes `statusBarHeight` from `useSafeAreaInsets().top` (line 48, 66)
- `src/components/Menu/SubMenu/SubMenu.tsx` - Does NOT pass `statusBarHeight` to inner PaperMenu
- `src/components/Menu/MenuItem/MenuItem.tsx` - Positions submenu anchor at `{x: pageX + width, y: pageY + height}` (line 139)
- `src/components/Selector/Selector.tsx` - Uses Menu (which passes `statusBarHeight` correctly)

### Target State
- PaperMenu accounts for bottom safe area inset (`insets.bottom`) in its scroll height calculation
- Menus with many items are properly scrollable on all device sizes
- The last menu item is fully accessible even on shorter phones like iPhone 16
- SubMenu passes `statusBarHeight` for Android correctness

## Implementation Plan

### Step 1: Extend PaperMenu patch to account for bottom safe area
**Files**: `patches/react-native-paper+5.14.5.patch`
**Status**: `DONE`

**Change**:
- [ ] Modify the `show` callback in PaperMenu to subtract `insets.bottom` from `windowLayout.height`
- [ ] Add `insets` to the `show` callback's dependency array

**Detailed Guidance**:

The change is to line 348-351 of the patched `node_modules/react-native-paper/src/components/Menu/Menu.tsx`:

```javascript
// BEFORE (line 348-351):
    setWindowLayout({
      height: windowLayoutResult.height - keyboardHeightRef.current,
      width: windowLayoutResult.width,
    });

// AFTER:
    setWindowLayout({
      height: windowLayoutResult.height - keyboardHeightRef.current - insets.bottom,
      width: windowLayoutResult.width,
    });
```

And update the dependency array at line 375:

```javascript
// BEFORE:
  }, [anchor, attachListeners, measureAnchorLayout, theme]);

// AFTER:
  }, [anchor, attachListeners, insets.bottom, measureAnchorLayout, theme]);
```

**Why this works**: `insets` comes from `useSafeAreaInsets()` at line 199 of PaperMenu. By reducing `windowLayout.height` by `insets.bottom`, all 13 downstream references to `windowLayout.height` in the scroll detection and height calculation logic automatically account for the bottom safe area. This means:
- The overflow detection triggers earlier (when menu would extend behind the home indicator)
- The scrollable height is reduced to fit the usable area
- The max height cap is reduced accordingly
- On devices with no home indicator (or Android hardware nav), `insets.bottom` is 0, so behavior is unchanged

**How to create the patch**:
1. First, make the change directly to `node_modules/react-native-paper/src/components/Menu/Menu.tsx`
2. Run `npx patch-package react-native-paper` to regenerate the patch file
3. Verify the patch applies cleanly: `npx patch-package --patch-dir patches`

**Pattern Reference**: Existing patch at `patches/react-native-paper+5.14.5.patch` (lines 1-69) shows the convention. The new changes extend the same file's `show` callback.

### Step 2: Pass statusBarHeight to SubMenu
**Files**: `src/components/Menu/SubMenu/SubMenu.tsx`
**Status**: `DONE`

**Change**:
- [ ] Import `useSafeAreaInsets` in SubMenu
- [ ] Pass `statusBarHeight={insets.top}` to the inner PaperMenu

**Code Guidance**:

```typescript
// src/components/Menu/SubMenu/SubMenu.tsx
import React from 'react';

import {
  Menu as PaperMenu,
  MenuProps as PaperMenuProps,
} from 'react-native-paper';
import {useSafeAreaInsets} from 'react-native-safe-area-context';

import {useTheme} from '../../../hooks';

import {createStyles} from './styles';

interface SubMenuProps extends Omit<PaperMenuProps, 'theme'> {}

export const SubMenu: React.FC<SubMenuProps> = ({
  visible,
  onDismiss,
  children,
  style,
  ...menuProps
}) => {
  const theme = useTheme();
  const styles = createStyles(theme);
  const statusBarHeight = useSafeAreaInsets().top;

  return (
    <PaperMenu
      visible={visible}
      onDismiss={onDismiss}
      style={[styles.menu, style]}
      contentStyle={styles.content}
      statusBarHeight={statusBarHeight}
      {...menuProps}>
      {children}
    </PaperMenu>
  );
};
```

**Pattern Reference**: See `src/components/Menu/Menu.tsx:48,66` where the parent Menu already gets `statusBarHeight` from `useSafeAreaInsets().top` and passes it to PaperMenu. SubMenu should do the same.

**Why**: On Android, PaperMenu's `additionalVerticalValue` uses `statusBarHeight ?? insets.top`. Without explicit `statusBarHeight`, PaperMenu falls back to its own `insets.top` from `useSafeAreaInsets()`, which should be the same value. However, explicitly passing it ensures consistent behavior and matches the parent Menu pattern. On iOS, `additionalVerticalValue` is always 0 regardless, so this change has no iOS effect -- it's purely for Android correctness and code consistency.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Patch affects all menus, not just model dropdowns | Med | Low | `insets.bottom` is only 34pt on modern iPhones; for menus that already fit within the safe area, the reduced available height doesn't trigger scrolling (the overflow detection at line 507 still evaluates to false). Only menus that would extend behind the home indicator are affected. |
| PaperMenu dependency array change causes unnecessary re-renders | Low | Low | `insets.bottom` is stable for a given device orientation. It only changes on orientation change (which already dismisses menus via the Dimensions change listener). |
| Future react-native-paper upgrade may conflict with extended patch | Med | Med | The patch is well-documented and small. When upgrading RNP, check if the upstream Menu component has been updated to account for safe area insets. |
| Upward-expanding menus (menu opens above anchor) may lose bottom space unnecessarily | Low | Low | The reduced `windowLayout.height` affects upward expansion too, but by only ~34pt. The menu would still expand upward correctly. The usable area IS genuinely smaller, so this is correct behavior. |
