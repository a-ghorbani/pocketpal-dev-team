### Background
A VPE review of the PACT (Pal-Activated Capability Toolkit) code identified metadata shape and dispatch coupling issues. These are dramatically cheaper to fix before shipping than after (persisted metadata in SQLite would require data migration). The founder approved doing all fixes in this branch before shipping.

### Current State

**Metadata shape** (`useChatSession.ts:422-442`): The dispatch loop extracts individual fields from `TalentResult` and spreads them as flat metadata keys:
```ts
...(htmlPreview ? {htmlPreview} : {}),
...(htmlPreviewTitle ? {htmlPreviewTitle} : {}),
```
Adding a new visual talent requires adding new metadata field names — a metadata "leak."

**`talentResults` naming collision** (`useChatSession.ts:440`): The field `metadata.talentResults` holds `Array<{tool_call_id, content}>` — the OpenAI wire-format payload for next-turn history reconstruction. This name collides with the desired result-keyed map.

**TalentSurface only renders `talentCalls[0]`** (`TalentSurface.tsx:31`): `const talentName = talentCalls[0].function.name;` — only first call rendered.

**Title sourced from `parsedArgs`** (`useChatSession.ts:407-409`): Title is extracted from `parsedArgs.title` in the dispatch loop rather than coming from the `TalentResult` itself.

**`talentCallPending` is boolean** (`useChatSession.ts:301`): A single boolean flag with no per-talent resolution.

**Tool schemas duplicated** (`PalStore.ts:724-823`): Three tool schema literals are hand-written in the Code Companion Pro seed, duplicating knowledge that belongs in each engine.

### Target State

1. **Result-keyed metadata**: `metadata.talentResults: { [callId: string]: TalentResult }` — the dispatch loop stores the full typed result keyed by the unique call ID (`tc.id`). TalentSurface looks up results via `talentResults?.[tc.id]` and maps to UI renderers via `talentUIRegistry.get(tc.function.name)`. This eliminates the duplicate-call key collision entirely (call IDs are unique per call, backfilled in the dispatch loop).
2. **Wire payload renamed**: `metadata.toolMessages` holds `Array<{tool_call_id, content}>` (was `talentResults`).
3. **TalentSurface iterates all calls**: Renders each talent's UI, not just `[0]`.
4. **Title in TalentResult**: `title?: string` on the html variant; `RenderHtmlEngine.execute()` populates it.
5. **`pendingTalentNames: string[]`** replaces `talentCallPending: boolean`.
6. **`toToolDefinition()` on TalentEngine**: Each engine owns its schema; PalStore seed derives schemas from the registry. Return type is a concrete `ToolDefinition` interface (not bare `object`).

  ```tsx
  export const TalentSurface: React.FC<TalentSurfaceProps> = ({metadata}) => {
    if (!metadata) return null;

    const talentCalls = metadata.talentCalls as
      | Array<{function: {name: string}; id: string}>
      | undefined;
    const talentResults = metadata.talentResults as
      | Record<string, TalentResult>
      | undefined;
    const pendingTalentNames = metadata.pendingTalentNames as string[] | undefined;

    // Result phase: iterate all talent calls
    if (talentCalls && talentCalls.length > 0) {
      const rendered: React.ReactNode[] = [];

      for (const tc of talentCalls) {
        const name = tc.function.name;
        const ui = talentUIRegistry.get(name);
        if (!ui) continue;

        // Look up result by call ID (unique per call), UI renderer by talent name
        const result = talentResults?.[tc.id];
        if (result && ui.renderResult) {
          const node = ui.renderResult(result);
          if (node != null) {
            rendered.push(<React.Fragment key={tc.id}>{node}</React.Fragment>);
            continue;
          }
        }

        // Per-talent pending
        if (pendingTalentNames?.includes(name) && ui.renderPending) {
          rendered.push(
            <React.Fragment key={tc.id}>{ui.renderPending()}</React.Fragment>,
          );
        }
      }

      if (rendered.length > 0) return <>{rendered}</>;
      return null;
    }

    // Pending phase: no talentCalls yet (early streaming)
    if (pendingTalentNames && pendingTalentNames.length > 0) {
      // Try talent-specific pending for known names
      const specific = pendingTalentNames
        .map(name => talentUIRegistry.get(name))
        .filter(ui => ui?.renderPending)
        .map((ui, name_idx) => (
          <React.Fragment key={pendingTalentNames[name_idx]}>{ui!.renderPending!()}</React.Fragment>
        ));
      if (specific.length > 0) return <>{specific}</>;

      // Generic fallback
      return (
        <View testID="talent-call-pending" style={{paddingHorizontal: 12, paddingVertical: 8}}>
          <Text style={{fontStyle: 'italic', opacity: 0.7}}>Generating preview…</Text>
        </View>
      );
    }

    return null;
  };
  ```

  **Note on keys**: In the "Pending phase" section, keys use the talent name from `pendingTalentNames` (stable string) rather than array index. In the "Result phase", keys use `tc.id` (unique call ID). This avoids unstable `key={i}` patterns.
