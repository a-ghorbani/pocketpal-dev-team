### Background
When a thinking-capable model (e.g., QwQ, DeepSeek-R1) is used with `enable_thinking: true`, the model returns both `reasoning_content` (the thinking/reasoning block) and `content` (the final answer). During streaming, the thinking block is visible to the user. However, once completion finishes, the thinking block disappears and is no longer shown or available for copy/context.

GitHub issue #575 reports: "the thinking blocks disappear at the end of the text creation and do not also appear in the overall conversation context."

### Current State

**Streaming phase (works correctly):**
- `useChatSession.ts:282-306` - During streaming, each token callback saves `reasoning_content` into `metadata.partialCompletionResult.reasoning_content` via `updateMessageStreaming()`.
- `ChatSessionStore.ts:508-517` - `updateMessageStreaming()` correctly **merges** metadata: `{...(message).metadata, ...update.metadata}`. This preserves existing metadata keys while adding new ones.
- Result: During streaming, `partialCompletionResult.reasoning_content` is present in metadata and the thinking block is visible.

**Post-completion phase (broken):**
- `useChatSession.ts:334-348` - After completion, `updateMessage()` is called with a new `metadata` object containing only `timings`, `copyable`, and `multimodal`. It does NOT include `completionResult` with the final `reasoning_content`.
- `ChatSessionStore.ts:546-551` - `updateMessage()` uses `{...session.messages[index], ...update}` which performs a shallow spread. Since `metadata` is a top-level key in `update`, the entire `metadata` object is **replaced** (not merged), wiping `partialCompletionResult` that held `reasoning_content`.
- Result: After completion, `partialCompletionResult` is gone, `completionResult` was never set, so both fallback paths in the rendering code return `undefined`.

**Rendering code (correct, reads both paths):**
- `TextMessage.tsx:248-249` - Reads `metadata?.completionResult?.reasoning_content || metadata?.partialCompletionResult?.reasoning_content`
- `chat.ts:44-45` - Same pattern for building chat context

**Database layer (correct, already merges):**
- `ChatSessionRepository.ts:494-499` - `updateMessage()` already merges metadata: `{...existingMetadata, ...update.metadata}`. The DB is fine; the problem is the in-memory store.

### Target State
1. `ChatSessionStore.updateMessage()` should merge `metadata` the same way `updateMessageStreaming()` does, preserving existing metadata keys (like `partialCompletionResult`) when new metadata (like `timings`) is added.
2. `useChatSession.ts` should additionally save `completionResult` with the final `reasoning_content` and `content` from the completion result, so that the authoritative final data is available (not just the streaming partial).

After the fix:
- Thinking blocks remain visible after completion finishes
- Chat context builder includes reasoning_content in subsequent prompts
- Copy includes the thinking content
- Both `completionResult` (final) and `partialCompletionResult` (streaming) are preserved in metadata

### Step 1: Fix metadata merge in ChatSessionStore.updateMessage()
**Files**: `src/store/ChatSessionStore.ts`
**Status**: `DONE`

**Change**:
- [ ] In `updateMessage()` method (line 546-551), change the message update to merge `metadata` instead of replacing it, matching the pattern in `updateMessageStreaming()` (lines 512-516)

**Pattern Reference**: See `src/store/ChatSessionStore.ts:508-517` (`updateMessageStreaming` -- the correct pattern)

**Code Guidance**:
```typescript
// BEFORE (line 546-551) -- replaces metadata entirely:
runInAction(() => {
  session.messages[index] = {
    ...session.messages[index],
    ...update,
  } as MessageType.Text;
});

// AFTER -- merge metadata like updateMessageStreaming does:
runInAction(() => {
  const existingMessage = session.messages[index] as MessageType.Text;
  const mergedUpdate = {...update};

  // Merge metadata instead of replacing, to preserve existing fields
  // (e.g., partialCompletionResult from streaming)
  if (update.metadata !== undefined && existingMessage.metadata) {
    mergedUpdate.metadata = {
      ...existingMessage.metadata,
      ...update.metadata,
    };
  }

  session.messages[index] = {
    ...existingMessage,
    ...mergedUpdate,
  } as MessageType.Text;
});
```

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Metadata merge could overwrite intentional replacements | Low | Low | The only callers of `updateMessage` are the final completion update and message editing -- neither intends to wipe metadata. The DB layer already merges. |
| `result.reasoning_content` might be undefined for non-thinking models | Low | Low | This is fine -- `completionResult.reasoning_content` will be `undefined`, and the rendering code handles this gracefully with the `||` fallback chain. |
