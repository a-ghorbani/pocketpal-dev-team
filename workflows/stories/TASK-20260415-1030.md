## Context (For Recovery After Context Reset)

### Background

PocketPal's current chat loop (`src/hooks/useChatSession.ts`) has **zero tool-use
handling**. The `CompletionResult` type at `src/utils/completionTypes.ts:75`
explicitly strips `tool_calls` (and the comment at line 73 says so). The
`LocalCompletionEngine.completion()` at `src/api/completionEngines.ts:34-48`
maps `NativeCompletionResult` → `CompletionResult` and **drops `tool_calls`
on the floor**.

The design doc proposes a premium "Code Companion Pro" Pal that renders
model-generated HTML inline in chat via tool calling. The PocketPal-side work
is the foundational tool-use infrastructure — generalizable across any future
tool-enabled Pal — plus one concrete tool (`render_html`), one bubble type
(`HtmlPreviewBubble`), and a local dev fixture Pal for testing.

Palshub/Stripe/marketplace work is explicitly out of scope for this MVP.
Local dev fixture is sufficient for v1 integration and QA.

### Target State

1. **tool_calls plumbing (generalizable)**: `CompletionResult` carries
   `tool_calls`; `LocalCompletionEngine` forwards them (final result).
   `CompletionStreamData` *also* forwards `tool_calls` + `accumulated_text`
   from streaming `TokenData` to support the streaming placeholder.
2. **ToolHandlerRegistry** keyed by tool NAME; `RenderHtmlHandler` registered
   once at app init. **No palId hardcoding** anywhere.
3. **HtmlPreviewBubble** component: 250px collapsed, tap-to-fullscreen modal,
   CSP-locked, JS disabled, navigation blocked. **No sanitizer regex** (CSP
   is the guard).
4. **Pal spec extensions** (generalizable, not Code-Companion-specific):
   - `tools?: string[]` — Pal declares platform tool names to enable.
   - `greeting?: { text: string }` — optional UX-only greeting; NOT persisted
     as a real message, NOT sent to the model, visually distinct from real
     assistant bubbles.
5. **useChatSession**: after `await completionPromise`, if `result.tool_calls`
   is non-empty AND the active Pal declares `tools.includes(toolName)` AND a
   handler is registered, execute the handler; store `toolCalls` + `toolResults`
   + `htmlPreview` in `message.metadata` via the existing (metadata-merging)
   `updateMessage` path; verify state survives restart.
6. **Streaming placeholder**: when `data.tool_calls` is present in the
   streaming TokenData callback, show a skeleton "Generating preview…
   (N tokens)" bubble. **This is the sole detection signal** — no
   `accumulated_text` heuristic. llama.rn 0.12.0-rc.8 exposes `tool_calls`
   mid-stream (verified at `node_modules/llama.rn/src/index.ts:183`), which
   is sufficient. If in practice the UX feels choppy (e.g., placeholder
   appears late), file a follow-up — do not add heuristic fallbacks here.
7. **Graceful degradation**: on context init, check
   `modelStore.context.model.chatTemplates.jinja.toolUseCaps`. If absent
   AND the active Pal declares `tools`, show a **one-time** banner
   ("This model does not support tool calling. Output will appear as markdown
   code instead.") gated by an MMKV flag — not on every send.
8. **Soft cap**: at ≥4 HTML previews in current conversation messages, show
   an inline banner ("Start a new chat for best performance") — warns the
   user BEFORE the 5th preview renders. No enforcement.
9. **Dev-fixture Pal "Code Companion Pro"**: created on first run via
   `PalStore.initializeCodeCompanionProPal()`, following the existing
   `initializeLookiePal` pattern. Declares `tools: ['render_html']`, system
   prompt from design doc §5, greeting text, Qwen2.5-Coder-7B-Instruct
   recommended via `defaultModel`.

## Requirements

### Functional

1. **[MUST]** `CompletionResult` includes `tool_calls?: Array<ToolCall>`
   matching the llama.rn `ToolCall` shape.
2. **[MUST]** `CompletionStreamData` includes `tool_calls?` and
   `accumulated_text?` from llama.rn `TokenData`.
3. **[MUST]** `LocalCompletionEngine` forwards `tool_calls` in both the final
   result and the streaming callback.
4. **[MUST]** `OpenAICompletionEngine` must not regress; minimally: add
   `tool_calls: undefined` for now (tool calls for remote OpenAI SSE are
   out of scope but the type must not diverge).
5. **[MUST]** `ToolHandlerRegistry` resolves handlers by tool **name** only.
   No Pal-id coupling.
6. **[MUST]** `RenderHtmlHandler` returns `{ type: 'html', html, summary }`
   with **no regex sanitization** (CSP is the guard).
7. **[MUST]** `HtmlPreviewBubble` runs with:
   - CSP: `default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:`
   - `javaScriptEnabled={false}`
   - `originWhitelist={['about:blank']}`
   - `onShouldStartLoadWithRequest={() => false}`
   - 250px collapsed height, tap-to-fullscreen modal.
8. **[MUST]** Pal type gains `tools?: string[]` and `greeting?: { text: string }`.
9. **[MUST]** `local_pals` DB schema gains `tools` (JSON stringified `string[]`,
   optional) and `greeting` (JSON stringified, optional) columns; schema
   `version` bumped from 6 → 7 with a migration.
10. **[MUST]** `useChatSession` detects `result.tool_calls`, resolves via
    registry, executes handler, stores tool call + result + preview HTML in
    `message.metadata` through `chatSessionStore.updateMessage()` (which
    merges metadata — verified at ChatSessionStore.ts:564-568).
11. **[MUST]** Tool results feed back to the model on the NEXT user turn via
    `convertToChatMessages` extension so the model sees
    `{role: 'tool', tool_call_id, content}` in the context. (This is how
    multi-turn iteration works — "Make it blue" requires model to see prior
    tool result.)
12. **[MUST]** Sessions reloaded from DB after app restart render the
    HTML preview bubble with the correct HTML intact (metadata persistence
    verification).
13. **[MUST]** When the active model's
    `chatTemplates.jinja.toolUseCaps` is absent AND the active Pal declares
    `tools`, show a one-time banner. Flag stored in MMKV; reset per-model-id.
14. **[MUST]** Greeting bubble:
    - Rendered at the TOP of a chat session when Pal has `greeting.text`
      AND `session.messages.length === 0` (zero persisted messages).
    - **Hidden** as soon as `session.messages.length > 0` (i.e., immediately
      after the first user message is appended — no animation required).
    - NOT persisted as a real message in DB.
    - NOT included in `convertToChatMessages` when building completion context.
    - Visually distinct (different background, italic or smaller type, icon).
15. **[MUST]** Soft cap warning at ≥4 HTML previews per session: count
    previews in current session messages; if ≥ 4, render a non-blocking
    warning banner above the input ("Start a new chat for best performance").
    This warns the user BEFORE the 5th (memory-pressure) preview renders.
16. **[MUST]** Streaming placeholder: while a tool call's arguments are
    assembling (detected SOLELY by `data.tool_calls` being present in the
    streaming callback — no `accumulated_text` heuristic), replace the
    streamed text with a skeleton "Generating preview… (N tokens)" bubble
    on the in-flight assistant message. Once `result.tool_calls` arrives,
    swap to the real preview.
17. **[MUST]** First-run seed: `PalStore` creates a "Code Companion Pro" Pal
    (via `initializeCodeCompanionProPal()`) with `tools: ['render_html']`,
    `greeting: { text: ... }`, system prompt from design doc §5,
    `defaultModel` pointing at Qwen2.5-Coder-7B-Instruct Q4_K_M (if the
    model is in `defaultModels`; otherwise leave `defaultModel` unset and
    surface the recommendation in description).
18. **[SHOULD]** Fullscreen preview modal uses safe-area insets.

### Non-Functional

- **Performance**: >5 WebViews in a session is a known memory hazard on
  budget Android. Soft cap warning covers v1; lazy-render optimization is
  out of scope (per design doc).
- **Compatibility**: iOS + Android; WebView supported on both via
  `react-native-webview`.
- **Security**: CSP + `javaScriptEnabled={false}` + blocked navigation is
  the entire security model. NO regex sanitizer — it is security theatre
  and was explicitly cut.
