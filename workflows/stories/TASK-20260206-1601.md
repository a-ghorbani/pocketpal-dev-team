### Background

GitHub issue #555 reports that the Apple Shortcut "Ask Pal" integration returns only the first chunk of the response. The shortcut stops listening to the stream prematurely.

#### How this bug was introduced

The Apple Shortcuts feature was created on **Oct 23, 2025** (PR #459) when PocketPal used `@pocketpalai/llama.rn v0.8.0`. At that time, `LlamaContextWrapper.mm` was a **thin wrapper** that simply delegated to `[RNLlamaContext completion:onToken:]`. That Objective-C class internally handled everything correctly — `rewind()`, parameter forwarding, operation ordering — and shortcuts worked fine.

On **Dec 10, 2025**, llama.rn v0.10.0 migrated to JSI, which **deleted `RNLlamaContext.mm`** entirely. The completion logic moved to `cpp/jsi/RNLlamaJSI.cpp` (JSI-coupled, not callable from plain Objective-C++).

On **Dec 27, 2025** (commit `de032ed`, PR #515), `LlamaContextWrapper.mm` was rewritten to call the low-level C++ API directly since its delegation target no longer existed. This rewrite introduced the bugs — the thin wrapper became a thick implementation that missed critical steps from the original `RNLlamaContext` code.

A future improvement would be to add a high-level `executeCompletion()` method to the llama.rn C++ layer (not JSI-coupled) that both JSI and native callers could use, restoring the thin-wrapper pattern. For now, we fix the thick wrapper to match the correct completion flow.

#### Root cause

The root cause is in `LlamaContextWrapper.mm`, the Objective-C++ wrapper that provides native iOS App Intents access to the llama.rn C++ inference engine. The Dec 2025 rewrite introduced four bugs:

1. **Missing `rewind()` call**: The `rewind()` method resets completion state (`n_remain`, `n_past`, `has_next_token`, `stopped_*` flags, `generated_text`, etc.). Without it, on second and subsequent calls (e.g., after session cache regeneration runs a minimal 1-token inference, then the real inference runs), state from the previous completion leaks through. Specifically, `n_past` from the first call makes the second call think the prompt is already evaluated, and stale stop flags can cause immediate termination.

2. **Wrong operation ordering**: The wrapper calls `initSampling()` -> `loadPrompt()` -> `beginCompletion()`. The correct order is `rewind()` -> set params -> `initSampling()` -> `beginCompletion()` -> `loadPrompt()`. Note: the JSI path sets params BEFORE `rewind()` (which then clears `antiprompt` and `grammar`). Our fix intentionally places param-setting AFTER `rewind()` — this is better because stop words aren't cleared. The ordering matters because:
   - `rewind()` must come first to reset all state
   - Parameters and stop words must be set after `rewind()` (which clears them) but before `initSampling()`
   - `initSampling()` creates the sampler from `params.sampling`, so all sampling params must be set before this call
   - `beginCompletion()` sets `n_remain = n_predict` and `is_predicting = true`
   - `loadPrompt()` calls `common_sampler_accept(ctx_sampling, ...)` for each prompt token, so the sampler must be initialized first. It also sets `has_next_token = true` at the end.

3. **Missing sampling parameters**: The wrapper only forwards 6 sampling parameters (temperature, top_k, top_p, min_p, seed, n_predict) but the JSI path forwards 20+. Missing parameters include: `penalty_last_n`, `penalty_repeat`, `penalty_freq`, `penalty_present`, `mirostat`, `mirostat_tau`, `mirostat_eta`, `typical_p` (typ_p), `xtc_threshold`, `xtc_probability`, `n_probs`, `ignore_eos`. While not all are directly responsible for the "first chunk" bug, the missing penalty/mirostat params mean the sampler is initialized with default C++ values instead of the app's configured values, leading to inconsistent generation behavior.

4. **Missing stop word detection in token loop**: The token generation loop does not call `findStoppingStrings()`, which is how stop words are detected. The C++ `doCompletion()` does NOT internally check antiprompt/stop words — this must be done by the caller. Both the old `RNLlamaContext` and the JSI code call `findStoppingStrings()` in their loops. The wrapper only checks `stopped_word` flag, but this flag is only set by `findStoppingStrings()` which is never called. Note: this may not cause the "first chunk" symptom specifically, but means stop words won't work at all in shortcuts.

### Target State

The `completionWithParams:onToken:error:` method should follow the correct completion flow. Note on ordering: `rewind()` clears `params.antiprompt` and `params.sampling.grammar` (lines 32-33 of `rn-completion.cpp`). The JSI path sets these BEFORE `rewind()`, which means they get wiped — stop words are silently broken in the JSI path too (nobody notices because completions end via EOS token, not stop words). Our ordering places parameter and stop-word setting AFTER `rewind()`, which is the only correct approach if stop words should actually work:

1. Call `completion->rewind()` to reset all state
2. Set ALL sampling parameters on `_context->params` (matching JSI `parseCompletionParams`)
3. Set stop words on `_context->params.antiprompt`
4. Call `completion->initSampling()` (creates sampler with the updated params)
5. Call `completion->beginCompletion()` (sets n_remain, is_predicting)
6. Call `completion->loadPrompt(emptyMediaPaths)` (tokenizes and feeds prompt to sampler)
7. Check `completion->context_full` and return error if true
8. Enter token generation loop with proper `-1` token and `incomplete` checks

| rewind() clears state that session cache depends on | Low | Medium | rewind() resets completion state, not model/KV cache state. Session save/load operates on the model's KV cache which is separate. Verified: `rewind()` does not call `llama_memory_clear()` |
| Build failure due to C++ API changes | Very Low | High | The methods (rewind, initSampling, beginCompletion, loadPrompt) are all already used in the wrapper or the JSI path; no new API surface |

### Resolved
- "Why does the shortcut only get the first chunk?" -> Session cache warm-up (1-token inference) leaves stale completion state that prevents the second real inference from generating past the first token. Missing `rewind()` is the primary cause.
