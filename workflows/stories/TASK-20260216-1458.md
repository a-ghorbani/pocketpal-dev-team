### Background
Currently all language JSON files (en, id, ja, zh -- plus unused fr, ko, ru, zh_Hant) are eagerly imported at the top of `src/locales/index.ts`. This means all translation data (~336KB across 8 files) is parsed and loaded into JS memory at app startup, even though only one language is active at a time. Issue #568 requests lazy-loading non-English language files so only the selected language is loaded on demand.

### Current State

**`src/locales/index.ts`** (line 1-17): Eagerly imports `en.json`, `id.json`, `ja.json`, `zh.json` at the top level. Constructs merged translations for each language using `_.merge({}, enData, langData)`. Exports `l10n` as `{en, id, ja, zh}` (a static object with all four pre-merged translations) and a `t()` interpolation helper.

**`src/store/UIStore.ts`** (line 6-120): Imports `l10n` from `../locales`. Defines `AvailableLanguage = keyof typeof l10n`. Has `_language` observable (persisted via `mobx-persist-store`), `supportedLanguages` array `['en', 'id', 'ja', 'zh']`, a computed `language` getter (with fallback to `'en'`), and a computed `l10n` getter that returns `l10n[this.language]`.

**`App.tsx`** (line 61): Reads `l10n[uiStore.language]` synchronously to provide to `L10nContext.Provider`.

**Consumer pattern**: 96+ files consume l10n via either:
1. `useContext(L10nContext)` in React components (60+ files)
2. `uiStore.l10n` in stores/services/utils (20+ files)
3. `l10n[uiStore.language]` direct access (palshub-display.ts, App.tsx)
4. `l10n.en` as default parameter in utility functions (formatters.ts, index.ts)

**`src/utils/index.ts`** (line 34-36): Defines `L10nContext` with type `(typeof l10n)[keyof typeof l10n]` and default value `l10n.en`.

**`src/utils/index.ts`** (line 81-100): Defines `initLocale` with `keyof typeof l10n` as parameter type and a mapped type `{[key in keyof typeof l10n]: unknown}` for its own hardcoded dayjs locale require map. This is a **parallel language registry** that must stay in sync.

**`src/utils/palshub-display.ts`** (line 72-79, 157-165): Has module-level constants `PAL_FILTER_LABELS` and `PAL_SORT_OPTIONS` that read `l10n[uiStore.language]` at import time. **NOTE**: This is a pre-existing bug where these values get frozen at the initial language and do not update when language changes. This is out of scope for this task.

**`src/screens/SettingsScreen/SettingsScreen.tsx`** (line 68-83): Has a hardcoded `languageNames: Record<AvailableLanguage, string>` mapping language codes to display names (e.g., `ja: '日本語 (JA)'`). This is a **duplicate of the language list** that must stay in sync.

**`scripts/validate-l10n.js`** (line 45): Hardcoded `['id', 'ja', 'zh']` array for language validation. Does NOT auto-discover locale files.

### Target State

1. `en.json` remains eagerly loaded (always needed as fallback and for type inference).
2. Non-English language JSON files (`id.json`, `ja.json`, `zh.json`) are loaded lazily via `require()` inside getters -- Metro still bundles them, but they are not parsed into JS memory until first access.
3. A **language registry** in `index.ts` is the single source of truth for: language keys, display names, and lazy-loaded translations. Replaces hardcoded lists in UIStore, SettingsScreen, and mock.
4. Loaded languages are cached so subsequent accesses are instant.
5. The exported API shape (`l10n`, `t()`, `Translations`) remains compatible so all 96+ consumer files require zero changes.
6. `AvailableLanguage` type is exported from `index.ts` and re-exported from UIStore for backward compatibility.
7. `keyof typeof l10n` resolves to literal union `'en' | 'id' | 'ja' | 'zh'` (preserved by getter approach, unlike Proxy).
8. `validate-l10n.js` auto-discovers locale files instead of using a hardcoded list.
9. Adding a new language requires only **3 files**: the JSON file, the registry entry in `index.ts`, and a dayjs locale require in `initLocale`.

### Step 1: Refactor `src/locales/index.ts` -- Getter-based lazy-loading with registry
**Files**: `src/locales/index.ts`
**Status**: `DONE`

**Change**:
- [ ] Remove eager imports of `idData`, `jaData`, `zhData`
- [ ] Keep eager import of `enData` (needed for fallback and type inference)
- [ ] Create a `languageRegistry` object mapping language codes to metadata (display names)
- [ ] Derive `supportedLanguages` and `AvailableLanguage` from the registry
- [ ] Export `languageDisplayNames` for SettingsScreen
- [ ] Create a `getTranslations(lang)` function that uses an inline `require()` switch to load the JSON, merge with `enData`, cache, and return
- [ ] Replace the static `l10n` object with a getter-based object -- each non-en language has a getter that calls `getTranslations()` on first access
- [ ] Ensure `typeof l10n` resolves to a concrete object type with literal keys (NOT Record<string, ...>)

**Why getters instead of Proxy**:
A getter-based object is simpler, has zero TypeScript typing issues, is debugger-friendly, and `keyof typeof l10n` resolves correctly to literal unions. `Object.keys()`, `in` operator, and nested type access (`keyof typeof l10n.models.modelCapabilities`) all work natively. The only downside is one getter line per language -- trivially mechanical.

**Code Guidance**:
```typescript
import _ from 'lodash';
import enData from './en.json';
import type {Translations} from './types';

// ─── Language Registry (single source of truth) ──────────────────────
// To add a language: 1) add entry here, 2) place JSON in src/locales/,
// 3) add case to requireLanguageData(), 4) add getter to l10n object.
const languageRegistry = {
  en: {displayName: 'English (EN)'},
  id: {displayName: 'Indonesia (ID)'},
  ja: {displayName: '日本語 (JA)'},
  zh: {displayName: '中文 (ZH)'},
} as const;

export type AvailableLanguage = keyof typeof languageRegistry;
export const supportedLanguages = Object.keys(
  languageRegistry,
) as AvailableLanguage[];

export const languageDisplayNames: Record<AvailableLanguage, string> = {
  en: languageRegistry.en.displayName,
  id: languageRegistry.id.displayName,
  ja: languageRegistry.ja.displayName,
  zh: languageRegistry.zh.displayName,
};

// ─── Lazy Loading ────────────────────────────────────────────────────
const cache: Partial<Record<AvailableLanguage, Translations>> = {
  en: enData,
};

// Metro bundles these at build time, but JS doesn't parse them until require() is called
function requireLanguageData(lang: AvailableLanguage): object | null {
  switch (lang) {
    case 'id':
      return require('./id.json');
    case 'ja':
      return require('./ja.json');
    case 'zh':
      return require('./zh.json');
    default:
      return null;
  }
}

function getTranslations(lang: AvailableLanguage): Translations {
  if (cache[lang]) {
    return cache[lang]!;
  }
  const langData = requireLanguageData(lang);
  const merged: Translations = langData
    ? _.merge({}, enData, langData)
    : enData;
  cache[lang] = merged;
  return merged;
}

// ─── Getter-based l10n object ────────────────────────────────────────
// Looks like {en: Translations, id: Translations, ...} but only loads
// non-en languages on first property access.
export const l10n = {
  get en(): Translations {
    return enData;
  },
  get id(): Translations {
    return getTranslations('id');
  },
  get ja(): Translations {
    return getTranslations('ja');
  },
  get zh(): Translations {
    return getTranslations('zh');
  },
};

// NOTE: Do NOT use `as const` on the l10n getter object — `as const` on getters
// is a no-op (getters already lack setters) and would be misleading.

// ─── Interpolation helper (unchanged) ────────────────────────────────
export function t(
  template: string,
  params: Record<string, string | number>,
): string {
  return template.replace(/\{\{(\w+)\}\}/g, (_match, key) =>
    String(params[key] ?? `{{${key}}}`),
  );
}
```

**Key design decisions**:
1. **Getters over Proxy**: TypeScript resolves `keyof typeof l10n` to `'en' | 'id' | 'ja' | 'zh'` (literal union). `Object.keys()`, `in`, and nested type access all work natively. No traps needed.
2. **`languageRegistry` as const**: Single source of truth for language keys AND display names. `AvailableLanguage` is derived from its keys.
3. **`switch` for require map**: Metro statically analyzes `require()` to include files in the bundle, but the JS engine does not evaluate the module until the `require()` is actually executed at runtime.
4. **Cache**: Once loaded, the merged result is cached so subsequent accesses are instant. The getter checks cache first.
5. **No `as const` on l10n getter object**: `as const` on getters is a no-op (getters already lack setters). Omitting it avoids misleading code.
6. **Plain object for `languageDisplayNames`**: Direct property access from `languageRegistry` — avoids `Object.fromEntries` + type assertion that could hide errors.

**Note on `l10n.en` default parameters**: Functions in `src/utils/index.ts` (line 263, 293) and `src/utils/formatters.ts` (line 108) use `l10n.en` as default parameter values. Default parameter expressions are evaluated at call time, not at function definition time, so the getter is invoked correctly each time. Since `l10n.en` returns eagerly-loaded `enData`, there is no performance concern.

## Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Getter-based `as const` object loses `readonly` modifier vs current `{en, id, ja, zh} as const` | Very Low | Low | Getters are inherently read-only (no setter); TypeScript treats them correctly |
| `Object.keys(l10n)` triggers getters | None | N/A | `Object.keys()` does NOT invoke getters -- it only enumerates own property names. Lazy loading is preserved. |
| `JSON.stringify(l10n)` triggers all getters | Low | Low | This would load all languages, but no production code stringifies `l10n`. If debugging tools do, it's a one-time cost. |
| `initLocale` dayjs map drifts from `supportedLanguages` | Low | Low | Type annotation `Record<AvailableLanguage, unknown>` ensures compile error if a language is missing from the dayjs map |
| `palshub-display.ts` module-level constants frozen at initial language | Pre-existing | Low | Out of scope -- document as known issue. These constants were already frozen before this change. |

## Open Questions

### Resolved
- Metro does not support `import()` for JSON -> Using synchronous `require()` inside getters
- Loading indicator during language switch -> Not needed; `require()` is synchronous and near-instant
- `supportedLanguages` source of truth -> Registry in `index.ts`
- Proxy vs getters -> **Getters** (simpler, better TypeScript support, no typing edge cases)
- `languageNames` in SettingsScreen -> **Import from registry** (`languageDisplayNames` export)
- Unused locale files (fr, ko, ru, zh_Hant) -> **Excluded from require map** and getters; only validated by `validate-l10n.js` auto-discovery
- `initLocale` in `src/utils/index.ts` -> **Update types** to use `AvailableLanguage`; dayjs require map stays hardcoded (separate concern) but type-checked via `Record<AvailableLanguage, unknown>`
