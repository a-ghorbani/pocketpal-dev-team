### Background

An external VPE review of the Code Companion v2 feature identified that `TextMessage.tsx` has a hardcoded if/else chain for rendering talent outputs (lines 274-290). Adding a new visual talent (audio player, weather card, chart) would require editing `TextMessage.tsx`. The fix mirrors the engine registry (`TalentRegistry`) on the UI side so each talent can register its own renderer.

A second finding: no test currently proves that a brand-new talent registered at runtime (without touching `registerDefaultTalents`) works end-to-end. This test proves the architecture is genuinely extensible.

### Current State

- **`src/services/talents/TalentRegistry.ts`** — Map-based engine registry. `register(engine)`, `get(name)`, `has(name)`, `reset()`. Singleton exported as `talentRegistry`.
- **`src/services/talents/index.ts`** — `registerDefaultTalents()` registers `RenderHtmlEngine`, `CalculateEngine`, `DatetimeEngine`. Called from `PalStore` constructor (line 99).
- **`src/services/talents/types.ts`** — `TalentEngine` interface (`name`, `execute`) and `TalentResult` discriminated union (`html | text | audio | error`).
- **`src/components/TextMessage/TextMessage.tsx:274-290`** — Hardcoded rendering:
  - If `message.metadata?.htmlPreview` exists: render `<HtmlPreviewBubble>`
  - Else if `message.metadata?.talentCallPending`: render a pending skeleton text
  - Else: render nothing
- **`src/hooks/useChatSession.ts:297-302`** — During streaming, when `data.tool_calls` is present, sets `{metadata: {talentCallPending: true}}` via `updateMessageStreaming`. Crucially, at this point `talentCalls` is NOT stored in metadata — only `talentCallPending: true`.
- **`src/hooks/useChatSession.ts:421-443`** — After completion, the final `updateMessage` stores `talentCalls`, `talentResults`, `htmlPreview`, `htmlPreviewTitle` in metadata.
- **`src/components/HtmlPreviewBubble/`** — Existing visual component for HTML talent output (WebView with CSP).

### Target State

- **New `TalentUI` interface and `TalentUIRegistry` class** — parallel to `TalentEngine`/`TalentRegistry`. `TalentUI` interface defined in `TalentUIRegistry.ts` (co-located with its registry, keeps `types.ts` framework-agnostic).
- **New `TalentSurface` component** — reads message metadata, looks up registered `TalentUI` by talent name in metadata, delegates rendering. When `talentCallPending: true` but no `talentCalls` present (streaming phase), renders a generic pending skeleton. Pure rendering component (no dispatch, no store access).
- **`TextMessage.tsx`** — replaces lines 274-290 with `<TalentSurface metadata={message.metadata} />`. No longer imports `HtmlPreviewBubble` directly.
- **`render_html` TalentUI registered** — maps `metadata.htmlPreview` to `<HtmlPreviewBubble>` via `renderResult(metadata)`.
- **Two integration tests**: (1) engine-side registry test proving runtime talent registration works, (2) UI rendering pipeline test proving TalentSurface renders a registered TalentUI.

**Files**: `src/services/talents/TalentUIRegistry.ts`
**Status**: `PENDING`

**Change**:
- [ ] Create `TalentUIRegistry.ts` with the `TalentUI` interface defined at the top of the file:
  ```typescript
  import React from 'react';

  export interface TalentUI {
    readonly name: string;
    /** Render the completed result. Receives the full message metadata dict. */
    renderResult?(metadata: Record<string, any>): React.ReactNode;
    /** Render a pending/loading state while the talent executes. */
    renderPending?(): React.ReactNode;
  }
  ```
- [ ] Below the interface, implement `TalentUIRegistry` class mirroring `TalentRegistry.ts` exactly (same Map pattern, same methods: `register`, `get`, `has`, `reset`)
- [ ] Export singleton `talentUIRegistry`

**Why `TalentUI` is in `TalentUIRegistry.ts` and not `types.ts`**: `types.ts` currently contains only framework-agnostic types (`TalentResult`, `TalentEngine`). `TalentUI` returns `React.ReactNode`, which is a React/UI concern. Co-locating the interface with its registry keeps `types.ts` clean and mirrors how the interface is consumed (always alongside the registry).

**Why `renderResult` takes `metadata: Record<string, any>` instead of `TalentResult`**: The dispatch loop in `useChatSession.ts` stores results as flat metadata keys (`htmlPreview`, `htmlPreviewTitle`), not as a `TalentResult` object. Constructing a fake `TalentResult` in `TalentSurface` would be dishonest about the data shape. Each `TalentUI` reads the metadata keys it knows about — `RenderHtmlTalentUI` reads `htmlPreview`/`htmlPreviewTitle`. When the dispatch loop is refactored to store result-keyed metadata, the signature can evolve to accept `TalentResult`.

**Pattern Reference**: Mirror `src/services/talents/TalentRegistry.ts:1-31` exactly. Same class structure, same method signatures, different type parameter (`TalentUI` instead of `TalentEngine`).

**Files**: `src/components/TalentSurface/TalentSurface.tsx`, `src/components/TalentSurface/index.ts`

**Change**:
- [ ] Create `TalentSurface.tsx` — a pure rendering component:
  ```typescript

  }
  ```
- [ ] Logic (two-phase lookup):
  1. **Result phase**: If `metadata?.talentCalls` exists (array of tool calls from final dispatch), extract the talent name from the first call's `function.name`. Look up `talentUIRegistry.get(talentName)`. If found and result data exists (e.g., `metadata.htmlPreview`), call `ui.renderResult(metadata)`. If no UI registered, render nothing (correct for text-only talents).
  2. **Pending phase**: If `metadata?.talentCallPending` is true AND step 1 did not render anything:
     - If `talentCalls` is present, use `talentUIRegistry.get(talentName)?.renderPending()` (talent-specific pending).
     - If `talentCalls` is NOT present (streaming phase — dispatch hasn't stored them yet), render a **generic pending skeleton** directly in TalentSurface:
       ```tsx
       <View testID="talent-call-pending" style={{paddingHorizontal: 12, paddingVertical: 8}}>
         <Text style={{fontStyle: 'italic', opacity: 0.7}}>Generating preview…</Text>
       </View>
       ```
     This preserves current behavior exactly: during streaming, the user sees the skeleton regardless of which talent is being called.
  3. Otherwise: render nothing.
- [ ] Keep it simple: no hooks beyond basic React, no store access, no MobX observer wrapping
- [ ] Create `index.ts` barrel export
- [ ] Add export to `src/components/index.ts`

**Design constraint**: The component must work with the CURRENT metadata shape (`htmlPreview`, `htmlPreviewTitle`, `talentCallPending`, `talentCalls`). It does NOT assume a result-keyed metadata format — that refactor is deferred.

**Why generic pending when talentCalls absent**: During streaming, `useChatSession.ts:297-302` sets `{talentCallPending: true}` but does NOT store `talentCalls` in metadata. That only happens in the final `updateMessage` call (line 439). So during the streaming phase, TalentSurface cannot know which talent is active. The generic skeleton matches current behavior — the hardcoded code at TextMessage.tsx:280-289 also doesn't check which talent is pending.

```typescript
export class TalentRegistry {
  private engines = new Map<string, TalentEngine>();

  register(engine: TalentEngine): void {
    this.engines.set(engine.name, engine);
  }

  get(name: string): TalentEngine | undefined {
    return this.engines.get(name);
  }

  has(name: string): boolean {
    return this.engines.has(name);
  }

  reset(): void {
    this.engines.clear();
  }
}

export const talentRegistry = new TalentRegistry();
```
