## Context

### Background

PR #702 introduced the E2E benchmark-matrix spec (model × quant × backend on Android) plus the `BenchmarkRunnerScreen` automation harness, comparison script, baseline file, and `e2eReleaseE2e` build flavor. The round-1 reviewer (`workflows/reviews/PR-702/round-1/final.md`) returned `REQUEST_CHANGES` with 10 findings spanning Architecture / Tests / Security / Data / Platform.

This revision addresses every finding the planner accepts as valid. One finding (B1, prod DCE leak via static `App.tsx` import) is deliberately **not** restructured — see the Review History row for the rationale (CI bundle-grep at `.github/workflows/ci.yml:202-233` is the empirical contract; the import-site argument is over-cautious). A doc-only callout is added so future readers don't reopen the same question.

### Current State (the bugs being fixed)

1. **`e2e/specs/benchmark-matrix.spec.ts:98-99`** — terminal-status check ignores per-cell failures. A matrix where every cell throws but the loop completes still passes the spec.

2. **`e2e/scripts/benchmark-compare.ts:165`** — `pass` is computed only from overlap rows: `rows.every(r => !r.flagged)`. A truncated current report missing baseline rows passes silently; `missing_in_current` is reported but does not affect the verdict.

3. **`e2e/scripts/benchmark-compare.ts:95-138`** — `pctDelta` returns `null` when either side is null, and `compareReports` does not consider `status`. A row that flips `status:'ok' pp_avg:200` → `status:'failed' pp_avg:null` produces no flag.

4. **`.github/workflows/e2e-tests.yml:48-69`** — workflow writes a dummy `google-services.json` containing only the `com.pocketpalai` client, then runs `assembleE2eReleaseE2e` (which has `applicationIdSuffix '.e2e'` per `android/app/build.gradle:160`). The Google Services Gradle plugin (applied at `android/app/build.gradle:9`) requires a matching client and will fail the build. Workflow is `workflow_dispatch`-only so the bug is latent.

5. **`e2e/scripts/build-bench-config.ts:100` vs `e2e/helpers/bench-runner.ts:39`** — two config builders emit different `nr` values (1 vs 3). The committed POCO baseline was generated via the `nr: 1` path; the WDIO spec runs at `nr: 3`. Comparing them would systematically read protocol differences as improvements/regressions. Reports do not persist `bench` params, so the mismatch is silent.

6. **`src/__automation__/screens/BenchmarkRunnerScreen.tsx:340-346` (success) vs `:377-406` (catch)** — context release lives only on the success path. If `ctx.bench()` or `initContext` throws, the next cell starts with the previous cell's native context still alive in `modelStore`.

7. **`e2e/helpers/bench-runner.ts:22-26` and `e2e/scripts/build-bench-config.ts:131-135`** — both use shell-string interpolation through `execSync` for adb invocations, with `udid` / `args.out` flowing in from env vars and CLI args.

### Target State

After this revision:

- The spec fails when any cell has `status !== 'ok'` (B2).
- The compare script fails when `missing_in_current.length > 0` and when a row regressed from `ok` to non-`ok` status (B3, C1).
- The workflow's dummy `google-services.json` covers both `com.pocketpalai` and `com.pocketpalai.e2e` clients (B4).

The repo agrees on `nr: 3`. The committed POCO baseline (currently at `nr: 1`) is documented as needing a re-baseline as a follow-up — not part of this revision.
- `BenchmarkRunnerScreen` releases the llama context on every cell that successfully initialized one, regardless of whether the cell's bench succeeded (C3).
- All adb invocations use `execFileSync('adb', argv)` style (C4, C5).
- `src/__automation__/README.md` documents that the production-DCE contract is enforced by the CI bundle-grep gate, not by import-site purity (B1 doc-only callout).

**Files**: `e2e/specs/benchmark-matrix.spec.ts`
