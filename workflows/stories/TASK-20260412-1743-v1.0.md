## Context

### Background
Parent story TASK-20260412-1743 delivers Neural TTS v1 end-to-end. It is too large for a single PR, so it is split into three stacked sub-stories. This one is the foundation: it installs the native dependency, builds the TTS engine + store layer, and wires assistant-message streaming hooks — without introducing any user-facing UI.

R1 of this story landed a working but **non-streaming** completion callback that fires only after the LLM response is fully written. R3 (this revision) replaces that with a streaming interface so the user hears speech as the model produces it, not after a 30-second silence. The same revision restructures the service into per-engine folders to absorb the upcoming Supertonic, Kokoro, and Kitten engines without re-touching shared files.

### Current State (R1, on disk now)
- `@mhpdev/react-native-speech@1.3.0` pinned at SHA `3ae0094`. iOS + Android Release builds verified.
- Flat `src/services/tts/` with `SystemEngine.ts`, `SupertonicEngine.ts`, `engineRegistry.ts`, `audioSession.ts`, `constants.ts`, `types.ts`, `index.ts`.
- `TTSStore` with memory gate, persisted `autoSpeakEnabled` + `currentVoice`, AppState/session-change stop hooks, `play()`/`stop()`/`onAssistantMessageComplete()`.
- `useChatSession.ts:357` fires `ttsStore.onAssistantMessageComplete(messageId, finalText)` after the final `updateMessage()` writing `completionResult`.
- 32 passing tests covering the above.

### Latent UX bug found in R1 review
`onAssistantMessageComplete` fires only at the FINAL `completionResult` write. For a 30-second LLM response, the user hears 30 seconds of silence before TTS begins — defeating the point of auto-speak. The fix requires feeding text incrementally into a per-engine buffer that flushes on natural breakpoints.

### Target State (after R3)
- `src/services/tts/` reorganized into per-engine folders. Adding Kokoro/Kitten in v2 means creating a new folder, not editing shared files.
- `TTSEngine` exposes both `play()` (replay path, used by per-message play button in v1.1) and `playStreaming()` (auto-speak path, returns a `StreamingHandle`).
- `useChatSession` exposes three TTS hook points: start (first token), chunk (each streaming write), complete (flush remaining buffer).
- `TTSStore` subscribes to all three, holds the active `StreamingHandle` in `playbackState`, and cancels it on stop / chat switch / AppState background.
- `SystemEngine.playStreaming` is a real implementation: buffers tokens, splits on sentence-ending punctuation, enqueues each utterance via the fork's queue API.
- `SupertonicEngine.playStreaming` is a stub: silently accepts `appendText`, throws "not installed (enabled in v1.2)" on `finalize()`. Same v1.0 contract as today's stubbed `play()`.
- iOS `AVAudioSessionCategoryPlayback` and memory-gate semantics unchanged.
- No UI components. No bundled assets. No Supertonic model download.

3. **[MUST]** Define the streaming engine interface in `src/services/tts/types.ts`:

   ```ts
   export interface StreamingHandle {
     appendText(chunk: string): void;   // per token / chunk from LLM
     finalize(): Promise<void>;         // at completion; flushes remaining buffer
     cancel(): Promise<void>;           // on stop / chat switch / background
   }

   export interface TTSEngine {
     readonly id: EngineId;
     getVoices(): Promise<Voice[]>;
     isInstalled(): Promise<boolean>;

     // Replay path — per-message play button (v1.1). Plays full text in one call.
     play(messageId: string, text: string, voice: Voice): Promise<void>;

     // Auto-speak streaming path. Returns a handle the store feeds chunks into.
     playStreaming(messageId: string, voice: Voice): StreamingHandle;

     stop(): Promise<void>;
   }
   ```

4. **[MUST]** `SystemEngine.playStreaming` (real implementation):
   - Internal mutable string buffer + pending-utterance queue.
   - `appendText(chunk)`: append to buffer. Repeatedly extract the longest prefix ending in `[.!?]` followed by whitespace or end-of-string; for each extracted prefix, enqueue an utterance via the fork's per-utterance queue API and remove it from the buffer.
   - `finalize()`: enqueue any remaining buffered text (even without terminal punctuation) so trailing partial sentences are spoken; resolve when the queue drains or immediately after enqueue (consistent with how `play()` resolves today).
   - `cancel()`: clear buffer, call `engine.stop()`, mark handle dead so subsequent `appendText`/`finalize` are no-ops.
   - Idempotent: a finalized or cancelled handle ignores further calls.

5. **[MUST]** `SupertonicEngine.playStreaming` (stub):
   - Returns a handle whose `appendText` accumulates silently.
   - `finalize()` rejects with `new Error('Supertonic not installed (enabled in v1.2)')`.
   - `cancel()` resolves silently.
   - This mirrors the current `play()` stub contract and lets v1.0 tests exercise the streaming-handle lifecycle without the real engine.

6. **[MUST]** `useChatSession.ts` exposes three TTS hook points (replacing the single R1 callback):
   - `ttsStore.onAssistantMessageStart(messageId, voice)` — fires once when the assistant message begins streaming (first token received / message created). The `lastSpokenMessageId` guard moves here.
   - `ttsStore.onAssistantMessageChunk(messageId, chunkText)` — fires on each `updateMessageStreaming` write (or equivalent incremental write). `chunkText` is the **delta** appended in this write, not the cumulative text.
   - `ttsStore.onAssistantMessageComplete(messageId, finalText)` — kept (same name as R1, public callback name preserved). Now triggers `StreamingHandle.finalize()` to flush the remaining buffer rather than playing the whole text. If no streaming handle was ever created for this `messageId` (e.g., the user picked a voice mid-message, or the start callback was missed), fall back to `engine.play(messageId, finalText, voice)`.

   None of the three fire during re-hydration of historical messages.

7. **[MUST]** `TTSStore` subscribes to all three callbacks and holds streaming state:
   - `playbackState: { mode: 'idle' } | { mode: 'streaming'; messageId: string; handle: StreamingHandle } | { mode: 'playing'; messageId: string }` (or equivalent discriminated union).
   - `onAssistantMessageStart(messageId, voice)`: gate on `isTTSAvailable && autoSpeakEnabled && currentVoice && messageId !== lastSpokenMessageId`. Cancel any existing handle. Set `lastSpokenMessageId = messageId`. Resolve engine, call `engine.playStreaming(messageId, voice)`, store handle in `playbackState`.
   - `onAssistantMessageChunk(messageId, chunkText)`: if `playbackState.mode === 'streaming' && playbackState.messageId === messageId`, call `handle.appendText(chunkText)`. Otherwise no-op.
   - `onAssistantMessageComplete(messageId, finalText)`:
     - If a streaming handle exists for `messageId` → `handle.finalize()`, transition state to `idle` on resolve.
     - Else if gating passes (auto-speak path missed start) → fallback to `play(messageId, finalText, currentVoice)`.
     - Else no-op.
   - `stop()` / chat-session-change reaction / AppState→background: if a handle is active, `handle.cancel()`; if `play()` is active, `engine.stop()`. State → `idle`.
   - Supertonic's "not installed" error from `finalize()` is caught and logged; state returns to `idle`. (Matches R1's swallow-the-stub-error behavior.)

8. **[MUST]** Memory gate, persistence, store registration, `init()` wiring in `App.tsx`, iOS audio session category — all unchanged from R1.

#### Post-install caveats (discovered during R1)

The WIP fork ships without a built `lib/` directory and depends on git submodules that yarn's GitHub tarball fetch does not populate. Three manual steps were required to get native builds working; these need to be automated (postinstall script) before the PR is merged, OR documented in `CONTRIBUTING.md`.

1. **TypeScript shim**: the package has no prebuilt typings and `bob build --target typescript` fails against RN 0.82. Workaround: `src/types/shims/mhpdev-react-native-speech.d.ts` declares the subset of the API we call (`speak`, `stop`, `getAvailableVoices`, `VoiceProps`). **R3 must extend this shim** to declare the per-utterance queue API used by `SystemEngine.playStreaming` (e.g., `speakStream`, queue control). Remove the shim when the published package ships real `.d.ts`.

2. **espeak-ng submodule**: `node_modules/@mhpdev/react-native-speech/third-party/espeak-ng/` ships empty because yarn does not pull git submodules from GitHub tarballs. To populate:
   ```bash
   cd node_modules/@mhpdev/react-native-speech/third-party
   git clone https://github.com/espeak-ng/espeak-ng.git
   cd espeak-ng
   git checkout b0b605c8a80f76c4c19e18033c6780c3cc4afc5b
   git submodule update --init --recursive   # pulls ucd-tools
   ```
   Without this, the iOS `Build espeak-ng static library` script phase fails with `cp: .../libespeak-ng/config.h: No such file or directory`.

3. **Pod install ordering**: the RNSpeech podspec declares `vendored_frameworks = 'ios/build-espeak/libespeak-ng.xcframework'`. That path does not exist until the `before_compile` script runs, so the FIRST `pod install` does not add the framework reference to `Pods.xcodeproj`. After the first iOS build attempt generates the xcframework, run `bundle exec pod install` a second time to register the framework, then rebuild.

### R3 (filled by implementer)

**Approach chosen: Option A — JS-side sentence chaining via `onFinish` event** (human-approved over upstream fork change).

Fork API investigation found that `@mhpdev/react-native-speech@3ae0094` does **not** expose a true per-utterance native queue (`speakStream` etc.). What it does expose on the `Speech` default export is a set of event emitters:

- `Speech.onFinish: EventEmitter<{utteranceId?: string}>` — fires when the current utterance finishes playing.
- `Speech.onStart`, `onStopped`, `onError`, `onProgress`, `onPause`, `onResume` — companions.

Per the Risks table fallback ("sentence-by-sentence `speak()` calls chained on the JS side"), `SystemEngine.playStreaming` now drives the chain from JS:

1. Subscribe to `Speech.onFinish`.
2. Internal buffer + utterance queue.
3. `appendText(chunk)`: append, extract longest prefix ending in `[.!?。！？]` followed by whitespace or end-of-string, enqueue each extracted sentence. If not currently speaking and the queue has an item, call `Speech.speak(sentence, voiceId)`.
4. `onFinish` handler: pop next queued sentence and speak it; if queue empty, mark `speaking=false` and resolve any pending finalize.
5. `finalize()`: drain buffer (push any remaining text even without terminal punctuation), await queue drain.
6. `cancel()`: clear queue+buffer, `Speech.stop()`, unsubscribe `onFinish`, resolve pending finalize.

**Test #4 semantics** — adjusted from "3 enqueued utterances in the native queue" to "3 sequential `Speech.speak()` calls driven by `onFinish` chaining". Intent preserved (3 sentences → 3 utterances); mechanism is JS-driven rather than a native queue. Mock at `__mocks__/external/@mhpdev/react-native-speech.ts` exposes `__emitFinish()` / `__finishListenerCount()` / `__resetFinishListeners()` helpers so tests drive the chain without a real native module.

CJK terminator support (`。！？`) is included in the splitter regex — the Risks-table CJK limitation is now closed rather than deferred to v1.2.

**TypeScript shim** extended in `src/types/shims/mhpdev-react-native-speech.d.ts` to declare `Speech.onFinish` and its `EventEmitter`/`FinishEvent` types.

**Native builds** were not re-run in this R3 pass — the task instructions explicitly scoped out native builds ("No native builds needed"). R1 build verification still stands; the R3 changes touch only JS/TS files (no podspec, no native module boundary changes). Reviewer to re-verify builds in the final gate.
