## Context

### Background

This story redesigns tool calling on top of PR-705. To plan correctly,
you must understand TWO distinct code states — they are not the same.

#### Starting state (post-PR-705 tip, commit `1c1ecec`)

This is what the implementer's worktree contains when they start.

PR-705 introduced tool calling (PACT talents). At its tip:

- `useChatSession.ts` is **574 lines**.
- Tool dispatch is **single-turn**: the model emits `tool_calls`, the
  hook executes them, results are stored in metadata. There is **no
  follow-up loop** — text-result talents (calculate, datetime) leave the
  model without a chance to produce a natural-language answer using the
  tool result. (The `requiresModelResponse` flag exists in the talent
  type but the loop that would consume it does not.)
- Tool data is stored on existing `MessageType.Text` rows under
  `metadata.talentCalls` / `metadata.toolMessages` / `metadata.talentResults`.
  This is the wrong shape — see "Why redesign" below.
- The streaming path overwrites `update.text = content.replace(...)`
  on every token at `useChatSession.ts:325`. For single-turn responses
  this is fine; once a follow-up loop is added on top, this becomes
  the preamble-overwrite bug (see Failed forward path).
- Error rollback writes `metadata: {interrupted, copyable}` via
  `chatSessionStore.updateMessage` at `useChatSession.ts:497`. The
  function is type-gated on `type === 'text'`, which still works for
  PR-705's single-turn shape.
- No `setIsGeneratingToolCall` setter exists yet; `isGeneratingToolCall`
  isn't a flag at this commit.

PR-705 has not shipped to TestFlight or Play Store. The wrong on-disk
shape has zero production users. The current story corrects the shape
before any release.

#### Failed forward path (multi-turn branch — DO NOT use as base)

After `1c1ecec`, an effort to add the multi-turn follow-up loop on top
of the metadata-bag shape was attempted on `feature/TASK-20260415-1030`
(commits `62637c7` onward, currently at HEAD `4af889a`). That effort
exposed the structural problems this story exists to fix:

- Hook ballooned from 574 → **757 lines** (`handleSendPress` ~530 of
  them).
- Six imperative `setIsGeneratingToolCall` call sites were added to
  paper over status-flag races, producing a fragile UX that needed
  patching commits `fix... throttle race`, `fix... dead zone`,
  `Revert "fix... thinking bubble"`, `fix... thinking bubble` (again).
- The `// Follow-up text intentionally overwrites first-turn text`
  comment at `useChatSession.ts:588` (on the multi-turn branch)
  documents the preamble loss as intentional — because the data shape
  has only one `text` field per assistant message and no way to
  represent a preamble + tool call + final answer as a single logical
  reply.
- `convertToChatMessages` had to reconstruct the multi-turn API shape
  from metadata, forcing a mid-flight `chatSessionStore.updateMessage`
  write inside the agent loop solely to feed the next iteration's
  reconstruction.

This branch is abandoned. The new branch (this story) starts from
`1c1ecec` (pre-multi-turn) and adds the follow-up loop **on top of the
correct data shape from day one**.

#### Why redesign — and why now

The right shape is a new `MessageType.AssistantTurn` carrying
`steps: AgentStep[]`. Each step is one model invocation with its
emitted tool calls and the outcomes of executing them. With this shape:

- Preamble is preserved (it's `steps[0].content`, not overwritten).
- `convertToChatMessages` is a 1:1 map per step, no metadata reads.
- The loop becomes "for each event, write the active step" — small,
  testable, no mid-flight reconstruction.
- The state of "what's the agent doing right now" derives from a pure
  reducer over loop events, no imperative setter races.

Because PR-705 has not shipped, the wrong on-disk shape has zero
production users. We branch directly from PR-705's tip (`1c1ecec`),
implement the redesign, and PR-705 closes with a redirect to the new
PR when it opens. The wrong shape never reaches `main`. No schema
migration. No release-tag coordination.

### Behavior preservation

UI behavior matches PR #705 with **one** intentional change: preamble
text emitted before a tool call is preserved alongside the follow-up
answer instead of being overwritten. This is the win.

Everything else is structural. Any test needing a non-trivial semantic
edit is a yellow flag — stop and surface it in the PR description.

### Data model

`src/utils/types.ts` adds:

```typescript
export interface AgentToolCall {
  id: string;
  function: {name: string; arguments: string | Record<string, unknown>};
}

export interface AgentToolOutcome {
  callId: string;
  toolName: string;
  result: TalentResult;          // existing TalentResult union
  responseContent: string;       // what gets fed back to the model
}

export interface AgentStep {
  /** One model invocation. */
  content?: string;              // visible text from this turn
  reasoningContent?: string;     // thinking
  toolCalls?: AgentToolCall[];   // model-emitted tool calls
  toolOutcomes?: AgentToolOutcome[]; // execution results, parallel
  partial?: boolean;             // true while streaming
}

export namespace MessageType {
  export interface AssistantTurn extends BaseMessage {
    type: 'assistant_turn';
    steps: AgentStep[];
  }
  // existing Text, Image, etc. unchanged
}
```

The agent runner produces `AssistantTurn` for **every** new assistant
response (single-step or multi-step). Single-step no-tool turns are the
degenerate case `steps: [{content}]`.

Pre-#705 `MessageType.Text` assistant rows that exist in user DBs
continue to render via the legacy path. No migrator.

### Persistence

The `messages` schema is **NOT changed**. No WatermelonDB migration.

- `AgentStep[]` is JSON-serialized into `metadata.steps` on the existing
  `messages` row.
- `Message.toMessageObject()` gets an `assistant_turn` branch that lifts
  `metadata.steps` to the top-level `steps` field for the in-memory type.
- The asymmetry (top-level on type, nested on disk) is intentional:
  schema unchanged, type is ergonomic.
- **Lift semantics (pinned)**: the in-memory message has top-level
  `steps` ONLY. `Message.toMessageObject()` strips `steps` from the
  `metadata` it returns (so a consumer reading `message.metadata.steps`
  from the in-memory type gets `undefined`). The persistence layer
  (`ChatSessionRepository`) is the **sole writer** of `metadata.steps`
  on the way back to disk. Per-step actions (`pushAgentStep`,
  `appendToolOutcome`, `finalizeActiveStep`) write the whole `steps`
  array wholesale; never rely on shallow-merge behavior to update a
  subset of steps. This rule prevents `updateMessage({metadata:
  {interrupted: true}})` from interacting weirdly with the lifted
  `steps` field.
- The `text` column is left empty for `assistant_turn` rows. (Implementer
  may denormalize to `derivedText(message)` if any pre-existing query
  assumes assistant `text` is non-empty — grep first; expect not.)
- **Metadata merge semantics**: the existing `updateMessage` does a
  shallow `{...existing, ...update}` merge of `metadata`. With
  `metadata.steps` as a top-level key inside metadata, an update like
  `{metadata: {timings}}` preserves `steps`, and an update like
  `{metadata: {steps: newSteps}}` replaces wholesale. The new
  step-specific actions (`pushAgentStep`, `appendToolOutcome`,
  `finalizeActiveStep`) always write the whole `steps` array
  intentionally. Document this in code comments to avoid future
  surprises.

### Existing store update paths must widen for `assistant_turn`

`chatSessionStore.updateMessage` and `updateMessageStreaming` currently
type-gate on `message.type === 'text'` and accept
`Partial<MessageType.Text>`. They are used outside the new step-action
surface for at least:

- **Error rollback** (`useChatSession.ts:497` at base ref `1c1ecec`) —
  writes `metadata: {interrupted: true, copyable: true}` on the in-flight
  assistant message, which is now an `assistant_turn` row. Without
  widening, this silently no-ops and the rollback metadata is lost.
- **Final timings/copyable** at run end — currently written via
  `updateMessage`. The new design moves this into `applyEventToStore`
  on `run_finished`, but it still calls into the same store function.

**Required change**: `updateMessage` and `updateMessageStreaming` widen
their type gates to `'text' || 'assistant_turn'`, and the parameter
type widens from `Partial<MessageType.Text>` to a metadata-bearing
union (`Partial<MessageType.Text> | Partial<MessageType.AssistantTurn>`,
or simpler: a metadata-only `Partial<{metadata: ...}>` for paths that
only touch metadata). Pin in Step 2 implementation.

### API conversion

`convertToChatMessages` reads `steps` directly:

```
For each AssistantTurn message m:
  for each step s in m.steps:
    emit { role: 'assistant', content: s.content ?? '', tool_calls: s.toolCalls? }
    for each outcome o in s.toolOutcomes:
      emit { role: 'tool', tool_call_id: o.callId, content: o.responseContent }
```

Filter rule: include any `AssistantTurn` whose `steps` array is
non-empty, regardless of step content. This preserves `tool_call_id`
back-references across turns when a step has only tool_calls.

**Wire-shape rules** (pinned to remove ambiguity):

- `AgentToolCall.arguments` is **always serialized as a string** at the
  wire boundary, matching what the OpenAI/llama.rn API expects. The
  runner parses the string for execution (via `JSON.parse`) but does
  NOT change the wire shape. The TypeScript `string |
  Record<string, unknown>` union exists only because llama.rn returns
  the parsed object on output and accepts a string on input — we
  serialize back to string before emitting through
  `convertToChatMessages`.
- `reasoning_content` per step is **preserved on the wire** when
  present. Today's path attaches `reasoning_content` to the assistant
  API message (`chat.ts:124, 138`); the new conversion does the same
  per step that has `step.reasoningContent`.

Legacy `Text` messages keep their current branch.

`metadata.talentCalls`, `metadata.toolMessages`, `metadata.talentResults`,
`metadata.completionResult`, and `metadata.partialCompletionResult` are
deleted from every reader and producer. AC has zero-grep contracts on
these names.

### `derivedText(message)` helper

`AssistantTurn` has no `text` field; many consumers read `message.text`
(Bubble copy, ChatInput edit-as-context, drawer preview, search). One
helper in `src/utils/chat.ts`:

```typescript
export function derivedText(message: MessageType.Any): string {
  if (message.type === 'assistant_turn') {
    return (message.steps ?? [])
      .map(s => s.content)
      .filter((c): c is string => !!c && c.length > 0)
      .join('\n\n');
  }
  return ('text' in message && message.text) ? message.text : '';
}
```

Bubble copy and any other `.text` consumer that should observe "final
visible content" route through `derivedText`. Caps the type-bifurcation
surface to a single function.

**Known `.text` consumers that need routing through `derivedText` or
otherwise widening**:

- `src/components/Bubble/Bubble.tsx:~77` — copy. Use `derivedText`.
- `src/components/TextMessage/TextMessage.tsx:~211, ~224, ~245` —
  link-preview regex test, `LinkPreview` text prop, and markdown text.
  For AssistantTurn rendering, route the active step's `step.content`
  through, NOT `message.text` (because there is none). For legacy
  `Text` messages, keep `message.text` reads.
- `src/store/ChatSessionStore.ts:~317–322` — `updateSessionTitle` reads
  the LAST message of the session (not the first), gated on
  `type === 'text'`. Widen the gate to `'text' || 'assistant_turn'` and

  recent message** is an `assistant_turn` (greeting bubbles, single-reply

- `src/utils/exportUtils.ts:~35, ~94` — chat session export reads

- `src/hooks/useMessageActions.ts` — `handleCopy` already covered;
  `handleEdit` and `handleTryAgain` paths inspected (already

### Visual rendering (Option B, pinned)

An `AssistantTurn` renders as **N visual blocks in step order**, NOT one
merged bubble. Matches the existing `HtmlPreviewBubble` / `TalentSurface`
pattern and ChatGPT/Claude.ai conventions.

For a turn with steps `[s0, s1, ..., sN]`:

```
for each step si:
  if si.reasoningContent → thinking bubble
  if si.content          → text bubble fragment (one TextMessage)
  if si.toolCalls        → talent-call indicator (existing chip styling)
  if si.toolOutcomes     → per-talent UI via TalentUIRegistry
                           (HtmlPreviewBubble, calculate-result, etc.)
```

A calculate flow with preamble + final answer renders as:

```
[Text bubble: "Let me calculate that…"]      ← steps[0].content
[Talent chip: "calculate(...)"]               ← steps[0].toolCalls
[Talent result block: "= 42"]                 ← steps[0].toolOutcomes
[Text bubble: "The answer is 42"]             ← steps[1].content
```

**FlatList shape**: an AssistantTurn occupies **one FlatList row**.
Inside that row, the renderer iterates `steps` and emits N visual
blocks. Do NOT split an AssistantTurn into N FlatList rows — `keyExtractor`
collides on shared id, and turn-level long-press routing breaks across
multiple rows.

**Inner-block spacing**: the first visual block in an AssistantTurn
uses the same outer offsets/padding as the existing single Text bubble
(matches the legacy snapshot for single-step no-tool turns).
Subsequent blocks within the same turn use a fixed inter-block gap of
`theme.spacing.s` (or whichever spacing token already separates
`HtmlPreviewBubble` from a text bubble in the current code — match
that). No new spacing constants. The "single-step matches Text bubble
snapshot" Renderer test #1 is the contract.

**Avatar**: shown once per AssistantTurn (existing `nextMessageInGroup`
+ `showAvatar` logic operates per FlatList row, so this works for free
under the one-row choice).

**Long-press routing**: `selectedMessage` holds the AssistantTurn id.
Long-press on any visual block within the turn opens the same turn-level
menu.

### Agent runner

`src/services/agent/AgentRunner.ts` exports:

```typescript
export const runAgent: (options: AgentRunOptions) => AsyncIterable<AgentEvent>;
```

Where `AgentEvent` is a discriminated union:

```typescript
export type AgentEvent =
  | {type: 'run_started'; runId: string}
  | {type: 'step_started'; turn: number; isFollowUp: boolean}
  | {type: 'token'; delta: TokenDelta}
  | {type: 'marker_seen'; marker: string}      // grammar_triggers detection
  | {type: 'tool_call_started'; call: AgentToolCall}
  | {type: 'tool_call_finished'; outcome: AgentToolOutcome}
  | {type: 'step_finished'; result: EngineCompletionResult; turn: number}
  | {type: 'run_finished'; result: AgentRunResult}
  | {type: 'run_failed'; error: Error};

export interface AgentRunOptions {
  engine: CompletionEngine;
  initialParams: ApiCompletionParams;
  allowedTalentNames: string[];
  talentLookup: (name: string) => TalentEngine | undefined;
  triggerMarkers: string[];   // precomputed by the hook before each call
  messageId: string;
  maxTurns?: number;          // default 5
  signal?: AbortSignal;       // checked between turns
}
```

`triggerMarkers` is **precomputed by the hook**, not derived inside the
runner. This keeps the runner free of llama.rn-context coupling — the
chat-template formatter (`getFormattedChat`) lives on
`modelStore.context`, not on `engine`. The hook computes the array once
before each `runAgent` invocation and passes it in. Cache hits make
follow-up sends in the same session effectively free.

The runner has zero React, MobX, or store imports — verified by an
explicit unit test that loads the module via `jest.isolateModules` and
inspects the require cache.

`hitMaxTurns` returns `run_finished` (not `run_failed`); the hook
decides what to surface.

**Stop-mid-tool semantics**: when `signal.aborted` becomes true during
`executeOne()`, the in-flight tool's promise still resolves (current
talents are synchronous-ish; we don't cancel them). The runner emits
`tool_call_finished` for that outcome, then checks `signal.aborted` at
the next turn boundary and emits `run_finished` (no follow-up turn).
The outcome IS persisted, the loop terminates cleanly.

### State reducer (pure UX state)

`src/services/agent/agentStateReducer.ts` exports a pure
`(state, event) => state` reducer over `AgentEvent`. No async, no
side effects, no React.

```typescript
export interface AgentUiState {
  status:
    | 'idle' | 'preparing' | 'streaming_text'
    | 'generating_tool_call' | 'executing_tool'
    | 'streaming_followup' | 'done' | 'failed';
  pendingTalentNames: string[];
  hitMaxTurns: boolean;
}
```

Hand-rolled, ~60 lines. No XState.

`pendingTalentNames` is **not** an `AgentStep` field. Renderer derivation:
- Active run: read from `agentUiState.pendingTalentNames`. Empty array
  + status `generating_tool_call` → render generic "preparing tool" copy.
- Persisted steps: derive from `step.toolCalls[*].function.name`.

**Active-vs-persisted predicate** (pinned, removes ambiguity for
renderer): a message is "active" if AND ONLY IF (a) it is the LAST
message in `currentSessionMessages`, AND (b)
`agentUiState.status ∈ {preparing, streaming_text, generating_tool_call,
executing_tool, streaming_followup}`. Otherwise it is "persisted." The
renderer's TalentSurface and TextMessage paths take an explicit
`isActiveRun: boolean` prop computed from this predicate at the
ChatView level (single source of truth) so individual blocks within a
turn don't re-derive it.

## Coding Standards

  `useMessageActions.handleEdit` early-return is authoritative; no

## Open Questions

### Resolved (rationale baked into the spec)

- _`text` column for `assistant_turn` rows: leave empty or denormalize?_
  → **Empty.** Implementer audited (Step 2): the only DB-column reads of
  `msg.text` are in `exportUtils.ts` and `importUtils.ts`. Both already go
  through the in-memory message shape via the conversion path that Step 3
  routes through `derivedText`. No query path reads the column directly
  for assistant rows. Schema column is `isOptional: true`. Same pattern
  as existing non-text types (`image`, `file`) which also leave `text`
  unset.

- AssistantTurn for ALL new assistant responses (not just tool-using
  ones). Single-step no-tool turn is the degenerate case
  `steps: [{content}]`.
- New `MessageType.AssistantTurn` rather than optional `steps?` on
  `Text`. Cleaner discriminant; types reflect intent.
- Structured `AssistantTurn { steps[] }` rather than granular three
  message types. One assistant turn is one logical unit; copy /
  regenerate / delete operate on the turn, not internal steps. The
  OpenAI wire shape is a serialization concern handled by
  `convertToChatMessages`.
- `metadata.steps` JSON storage; no schema migration.
- Visual rendering is Option B: N visual blocks per turn within ONE
  FlatList row. Long-press routing is turn-level.
- Edit-disallow lives at the handler/menu layer (single source of
  truth); no store-level guard.
- `pendingTalentNames` derived (not an `AgentStep` field). Active run
  reads from `agentUiState`; persisted reads from `step.toolCalls`.
- `triggerMarkers` cache is a factory + `useRef`, not module-level state.
- Stop-mid-tool: in-flight outcome is recorded; abort fires at next
  turn boundary.
- Pure hand-rolled reducer; no XState dependency.
- `runAgent` has zero React/MobX/store imports (test-enforced).
- _Iterator vs callback runner signature?_ → Iterator. Committed in v6
  per external review (Section 3.5). Reasoning: the hook needs to drive
  reducer + per-step persistence in lockstep, which is naturally cleaner
  with `for await` than nested callbacks; the queue+resolver adapter is
  ~30 LOC, manageable. Backpressure tests #17/#18 are part of the spec.
- _Branching strategy: merge PR-705 → branch from main, vs branch from
  PR-705 tip directly?_ → Branch from PR-705 tip (`1c1ecec`). Avoids
  the wrong on-disk shape ever reaching `main`, eliminates the
  release-tag coordination, and skips the failed multi-turn branch
  entirely. Committed in v6.
- _Active-vs-persisted predicate for the renderer?_ → "Last message in
  `currentSessionMessages` AND `agentUiState.status` is in {preparing,
  streaming_text, generating_tool_call, executing_tool,
  streaming_followup}." Computed once at the ChatView level and passed
  down as `isActiveRun`. (External review Section 3.2.)
- _`Message.toMessageObject()` lift semantics — both top-level steps
  AND metadata.steps in memory, or just top-level?_ → Just top-level.
  `metadata.steps` is a persistence-layer detail; `toMessageObject()`
  strips it from the in-memory `metadata`. (External review Section 3.3.)
- _Legacy `metadata.talentCalls` / `metadata.talentResults` reader path
  — keep for pre-#705 data or delete entirely?_ → Delete entirely. PR-705
  never shipped, so no production user data exists with the old shape.
  Resolves AC #5 contradiction. (External review Section 3.1.)
