### Background

PR #702 (the benchmark-matrix E2E work on branch `feature/TASK-20260422-1905`, story `TASK-20260422-1905`) added a hidden `BenchmarkResultTrigger` component dropped straight into `src/components/` and mounted unconditionally in `App.tsx` — following the (bad) pattern set by `MemorySnapshotTrigger`. That is now two E2E-only components scattered in the product tree, unconditionally mounted in every release, with a deep-link dispatch branch (`src/hooks/useDeepLinking.ts:68-82`) that ships in production even though it exists only for the iOS memory-profile spec.

Rather than land PR #702 with the messy pattern and file a follow-up, we fold the architecture cleanup into the same PR so the first time this lands on `main` it looks clean. No transitional ugliness ever hits `main`.

### Why the user wants `releaseE2e` (not debug)

Direct quote from the user's brief, senior-engineer call:

> "that is the whole reason why we are doing this. we want prod condition so our perf numbers makes sense."

E2E perf measurements (benchmark-matrix) must run against an app whose compile/optimize/strip flags match `release`. A debug APK has different Hermes bytecode optimisation, different Proguard/R8 behaviour (when/if enabled), different native symbol stripping, and different scheduling. Numbers from a debug APK don't translate. A dedicated `releaseE2e` buildType that `initWith release` but flips `debuggable=true` (so `adb shell run-as` works for preseeded GGUF push) is the minimum deviation from prod that still makes the benchmark-matrix preseed workflow viable.

### Why iOS scheme work is deferred

`benchmark-matrix` (PR #702) is Android-only per the TASK-20260422-1905 story. The user's brief explicitly permits deferring iOS:

> "iOS equivalent — MAY be stubbed/deferred if iOS E2E isn't in active use (planner researches and decides). Android path must be complete."

Other iOS E2E specs (memory-profile, quick-smoke, load-stress, thinking) DO exist and run today. However:
- They hit the `ai.pocketpal` bundle id, unchanged by this refactor.
- `__E2E__` is a build-time constant injected via babel; `ios:build:e2e` (today, Release configuration) would bake `__E2E__=false` because no gradle hook passes `E2E_BUILD=true` on iOS. This means **iOS E2E specs would BREAK after this refactor lands** unless we also make iOS set `__E2E__=true` at build time.

The minimal fix for iOS, scoped into THIS task: make `ios:build:e2e` export `E2E_BUILD=true` before invoking xcodebuild, so Metro's bundle (invoked by Xcode's React Native build script phase) sees it and transform-define produces `__E2E__=true`. No new scheme, no xcconfig, no bundle-id separation. Coexistence on iOS (E2E app + prod app on the same device) is deferred to a dedicated follow-up — not blocking because the iOS E2E specs in CI / locally always overwrite the single `ai.pocketpal` install.

This keeps the scope surgical while ensuring NO E2E spec regresses.

   *
   * Supported protocols in v1:
   *   pocketpal://memory?cmd=snap::<label>
   *   pocketpal://memory?cmd=clear::snapshots
   */
  import type {DeepLinkParams} from '../services/DeepLinkService';

  /** Returns true if handled; false if caller should fall through. */
  export async function dispatchAutomationDeepLink(
    params: DeepLinkParams,
  ): Promise<boolean> {
    if (params.host === 'memory' && params.queryParams?.cmd) {
      const {takeMemorySnapshot, clearMemorySnapshots} =
        require('../utils/memoryProfile');
      const cmd = params.queryParams.cmd;
      if (cmd.startsWith('snap::')) {
        await takeMemorySnapshot(cmd.slice(6) || 'unnamed');
      } else if (cmd === 'clear::snapshots') {
        await clearMemorySnapshots();
      }
      return true;
    }
    return false;
  }
