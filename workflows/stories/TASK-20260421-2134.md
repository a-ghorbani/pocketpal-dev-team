## Context

### Background
FOU-86 asks that after a release workflow run, the iOS debug-symbol bundle (`PocketPal.app.dSYM.zip`) is attached as an artifact on the run summary. The goal is local symbolication of future App Store / TestFlight crashes against a known release build. This unblocks FOU-85 (which needs symbolicatable CI-built dSYMs) without adding any crash-reporting SDK.

The release workflow was recently extended (PR #697, TASK-20260420-1800) with an `ios_only: true` dispatch input that skips version bump + Android and rebuilds TestFlight from the current ref. The dSYM step must work on both dispatch paths.

### Current State
- `.github/workflows/release.yml:153-242` — `build_ios` job:
  - Runs on `macos-15`, gated on `build_android`'s result being `success` OR `skipped` (so the job runs on both the normal path and the `ios_only` path).
  - Last step is "Build and upload iOS app" (lines 231-242), which calls `bundle exec fastlane release_ios_testflight`.
  - No post-build step exists — nothing is retained after the job ends; the dSYM is discarded with the runner.
- `ios/fastlane/Fastfile:44-55` — the `release_ios_testflight` lane calls `build_ios_app` (gym) with `output_directory: "./build"` relative to `ios/`, so artifacts land in `ios/build/`. Gym emits `PocketPal.ipa` AND `PocketPal.app.dSYM.zip` in that directory.
- `ios/Podfile:20` — `use_frameworks! :linkage => :static` plus `$RNFirebaseAsStaticFramework = true`. All pods (llama.rn, hermes, Firebase, …) static-link into the main `PocketPal` binary. There are no companion `*.framework.dSYM` bundles to collect.
- `ios/PocketPal.xcodeproj/project.pbxproj:817,976` — release configs set `DEBUG_INFORMATION_FORMAT = "dwarf-with-dsym"`, so the dSYM is always produced when gym succeeds.
- `.version` (repo root) — holds the marketing version (`1.14.0` currently). Updated by the `bump_version` lane on the normal path before `build_ios` checks out `github.ref`; on `ios_only` it is whatever the caller's ref has.
- `ios/PocketPal.xcodeproj/project.pbxproj` — holds `CURRENT_PROJECT_VERSION` (build number, `137` currently). Updated by `increment_build_number_in_xcodeproj` on the normal path; untouched on `ios_only`.
- `.github/workflows/ci.yml:203`, `.github/workflows/e2e-tests.yml:109,222` — this repo already uses `actions/upload-artifact@v4` with repo-root-relative paths (e.g. `ios/build/PocketPal.ipa`). Same action version and path convention apply here.

### Target State
After any successful run of the release workflow (normal OR `ios_only`), the workflow run summary in GitHub exposes an artifact named like `ios-dsym-v<marketing_version>-build<build_number>` (e.g. `ios-dsym-v1.14.0-build137`) whose contents are `PocketPal.app.dSYM.zip`. The artifact is retained for 90 days.

If the TestFlight upload fails (known flaky: Apple agreements, App Store Connect infra) AFTER gym succeeded, the dSYM artifact is still retained so the build can be re-uploaded from a different box later and still be symbolicatable.

If gym itself fails, the dSYM does not exist — the upload step must not convert a gym failure into a "double failure" that masks the real error.

### Step 1: Add two steps to the `build_ios` job in `release.yml`

**Files**: `.github/workflows/release.yml`
**Status**: `DONE`
**Commit**: `ec7afd9`

**Change**:
- [ ] Add a step "Extract iOS version info" AFTER the "Build and upload iOS app" step (release.yml:231-242) that reads `.version` and `CURRENT_PROJECT_VERSION` from the checked-out tree and writes both to `$GITHUB_OUTPUT` for the next step.
- [ ] Add a step "Upload iOS dSYM" AFTER "Extract iOS version info" that uses `actions/upload-artifact@v4` with the dynamic name, the dSYM path, and `retention-days: 90`.
- [ ] Both new steps must have `if: always()` so they run even if the upstream TestFlight upload fails. (The extract step is a cheap `grep`/`cat` — no harm running it on failure; and the upload step needs it.)

**Pattern References**:
- `actions/upload-artifact@v4` usage in this repo: `.github/workflows/ci.yml:202-206`, `.github/workflows/e2e-tests.yml:108-112,218-222`. All three use a repo-root-relative `path`.
- `$GITHUB_OUTPUT` pattern: there is no pre-existing in-repo example of a step using `id:` + `$GITHUB_OUTPUT` in `release.yml`, so the implementer should follow the standard GitHub Actions docs pattern (set `id: version`, write `key=value` to `$GITHUB_OUTPUT`, reference as `${{ steps.version.outputs.key }}`).

**Code Guidance**:

Insert AFTER line 242 (end of "Build and upload iOS app" step) and BEFORE the end of `build_ios`:

```yaml
      # Step 9: Extract iOS version info for dSYM artifact naming
      - name: Extract iOS version info
        id: version
        if: always()
        run: |
          MARKETING_VERSION=$(cat .version | tr -d '[:space:]')
          BUILD_NUMBER=$(grep -m1 'CURRENT_PROJECT_VERSION' ios/PocketPal.xcodeproj/project.pbxproj | awk -F'= ' '{print $2}' | tr -d ' ;')
          echo "marketing_version=${MARKETING_VERSION}" >> "$GITHUB_OUTPUT"
          echo "build_number=${BUILD_NUMBER}" >> "$GITHUB_OUTPUT"
          echo "Extracted: v${MARKETING_VERSION} build ${BUILD_NUMBER}"

      # Step 10: Retain dSYM as a workflow artifact for crash symbolication (FOU-86)
      - name: Upload iOS dSYM
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ios-dsym-v${{ steps.version.outputs.marketing_version }}-build${{ steps.version.outputs.build_number }}
          path: ios/build/PocketPal.app.dSYM.zip
          retention-days: 90
          if-no-files-found: warn
```

Rationale for each field:
- `if: always()` (both steps) — we want the dSYM retained even if `upload_to_testflight` fails. TestFlight upload is a known flaky path (Apple agreements / ASC infra).
- `if-no-files-found: warn` — v4's default; written explicitly for the critic's sake. If gym itself failed, the file does not exist, and we want the step to log a warning and exit 0 rather than turn a gym failure into two failures.
- `retention-days: 90` — per the Linear ticket.
- Reading `.version` via `cat` — the file is a single line (e.g. `1.14.0\n`); `tr -d '[:space:]'` strips the trailing newline.
- Reading `CURRENT_PROJECT_VERSION` via `grep -m1 | awk` — the project.pbxproj has multiple occurrences (lines 516, 555, 783, 816, 933, 975) but all are kept in sync by `increment_build_number_in_xcodeproj`; `-m1` takes the first.

Why extract into a separate step instead of inline:
- `actions/upload-artifact@v4`'s `name:` is a template expression evaluated at step-setup time. To use shell-computed values there, you must go through `$GITHUB_OUTPUT` (or job-level env). Step outputs keep the logic local to `build_ios` — no job-wide env pollution.

| # | Risk | Likelihood | Impact | Mitigation |

## Open Questions

### For Human
- [ ] Artifact-name format: `ios-dsym-v1.14.0-build137` is proposed. Acceptable? Alternative: `PocketPal-v1.14.0-137-dSYM`. The proposed form is all-lowercase-kebab (GitHub's own convention) and starts with a stable prefix (`ios-dsym`) so artifacts sort together in the UI.
- [ ] Retention: 90 days per Linear ticket. Acceptable? GitHub's workflow-run retention is independent (90 days default, configurable). If the project's retention policy ever tightens, both need to move together.
- [ ] Pre-merge validation: is an `ios_only` dispatch on the feature branch acceptable for validation, or should we wait for the first post-merge release? An `ios_only` dispatch incurs a full iOS build (~15-20 min macOS-15 minutes) and may upload a TestFlight build from a feature-branch ref — both costs are real, so default assumption is "post-merge release is the final gate". Implementer/reviewer can override if needed.

### Resolved
- Why a single dSYM? — All pods static-link into the main `PocketPal` binary (`ios/Podfile:20`, `$RNFirebaseAsStaticFramework = true`). There are no `*.framework.dSYM` companions worth collecting.
- Why `if: always()`? — TestFlight upload is a known flaky path; we want the dSYM retained even when upload_to_testflight fails, so the build can still be symbolicated if it ever reaches the App Store via a re-upload.
- Why `if-no-files-found: warn` over `continue-on-error: true`? — `warn` is precise to "no files" (the only case where we want to swallow the error). `continue-on-error: true` would mask unrelated failures (e.g. network error uploading), which is strictly worse.
- Why `actions/upload-artifact@v4`? — Already established in this repo (`ci.yml:203`, `e2e-tests.yml:109,222`); v3 is deprecated by GitHub (Nov 2024).
- Why extract version into a separate step instead of inline in the `name:`? — `name:` is a template expression evaluated before the step runs; it cannot read shell variables, only `${{ ... }}` expressions. So a prior step must publish outputs via `$GITHUB_OUTPUT`.
